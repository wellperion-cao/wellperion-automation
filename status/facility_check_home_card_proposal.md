# 시설부 점검 home 카드 — 회차·이상 중심 재구성 (2026-07-14, 시우) — ✅ 구현 완료

**상태: 제안 단계 종료 → 같은 날 구현 완료·라이브 반영.** 아래 §1 진단은 최초 조사 기록(경위 보존용)이나 **핵심 전제가 틀렸음이 GM 정정으로 드러났다** — 시설부는 '1일 단일 회차'가 아니라 이미 다회차(⏱시작→종료→제출 반복)로 운영 중이며, 그 회차·이상 원본 데이터는 `action=weekly`가 아니라 이미 사용 중인 `action=board&key=FACILITY_CHECK_<date>` 보드 blob(`시설부 체계.html`이 제출마다 `submissions[]`로 누적)에 그대로 있었다. **결과: GAS 백엔드 변경 없이 프론트 3곳(추가 fetch 1개+파서 1개+카드 렌더 교체)만으로 구현 완료.** 실제 구현 내용·라이브 검증 결과는 문서 최하단 §5(현재 상태) 참고.

GM 지시(정정 전): "완료율(5/5)만 나오는데, 더 중요한 건 몇 회차 진행했고 어떤 이상이 있는지다" →
아래는 그 시점의 진단이며 §3-§4의 "GM 확인 필요" 항목은 이후 GM이 직접 정정·확정했다(§5 참고).

## 1. 데이터 가용성 진단 (실측)

| 데이터 | 백엔드(점검일지_facility 시트) | home 카드가 받는 API(`action=weekly&dept=facility`) |
|---|---|---|
| 회차(라운드) | ✅ col4 '회차' — 단, **2026-07-08 GM 결정으로 시설부는 이미 '1일' 단일 회차로 통합**(과거 오전조/오후조/마감조 잔재를 '1일'로 재라벨). 현재 제출 플로우(`시설부 체계.html` L3841)도 `round`를 항상 `'1일'`로 고정 전송 | ❌ `handleWeekly`(GAS `지원팀 일일점검.js` L3031)가 이 열을 읽어 내부 그룹핑 키로만 쓰고 **응답에 포함 안 함** |
| 이상건수 | ✅ col9 '이상건수' — 저장 시 `_facilityRangeHits()`로 자동 계산(L2917-2924) | ❌ 응답에 없음 |
| 이상내용 | ✅ col10 '이상내용' — 위 계산 결과를 `"항목명(필드):값"` 텍스트로 join(L2920,2924) | ❌ 응답에 없음 |
| 완료율(항목 단위) | ✅ | ✅ `{total, done, pct}` — 현재 home 카드가 쓰는 값 |

**결론: 회차·이상건수·이상내용은 `점검일지_facility` 스냅샷에 이미 저장되지만, home이 호출하는 `handleWeekly`가 그 열을 응답에 실어주지 않는다.** 프론트(`wellperion_guide(main).html`)는 별도로 항목별 시트의 `measure`(raw 측정값)만 받아 사우나·수영장 한정으로 클라이언트에서 이상 여부를 재계산 중(`FACILITY_RANGES` 미러, L10746-10789) — 서버가 이미 계산해둔 값과 사실상 같은 로직을 이중으로 돌리는 구조.

## 2. 필요한 조치 (GAS 백엔드 — COO 도메인이지만 라이브 배포 리스크로 GM/웰리 확인 후 진행)

`.deploy-check/지원팀 일일점검.js` `handleWeekly()` L3104-3117의 `result.map()`에 facility 한정으로 필드 3개 추가:

```js
// dept==='facility'일 때만: 점검일지_facility 스냅샷에서 해당 날짜의 최신 행을 찾아 round/issueCount/issueNote 첨부
round: <스냅샷 col3(회차)>,
issueCount: <스냅샷 col8(이상건수)>,
issueNote: <스냅샷 col9(이상내용)>
```
- 기존 total/done/pct 계산 로직(snapByDate)은 이미 같은 스냅샷 행을 순회하며 "날짜별 최신 제출시각" 채택 패턴을 쓰고 있어(L3079) 그 안에서 같이 뽑으면 됨 — **추가 로직 최소, 기존 집계 무변경(순수 추가 필드)**.
- support/parking dept 응답은 건드리지 않음(facility 분기 한정) → 회귀 위험 0에 가까움.
- 배포: clasp push 후 **/exec 새 버전 배포 필수**(웹앱 재배포 없으면 반영 안 됨 — 과거 함정 재확인).

## 3. GM 확인이 필요한 지점 (임의 결정 금지)

1. **"회차"의 의미** — GM 발언("몇 회를 진행하고 있는지")은 지원부처럼 하루 여러 회차(오전/오후/마감)를 기대하는 뉘앙스이나, 시설부는 이미 GM 확정으로 **하루 1회차('1일') 고정**임(2026-07-08). 백엔드 값을 그대로 노출하면 "1일 회차 진행 · 완료 X/Y"로 표시되어 "몇 회"라는 기대와 다를 수 있음.
   - 옵션 A: 현재 설계(1일 1회차) 그대로 "오늘 점검 진행 여부"로 노출 — 데이터 지어내지 않음.
   - 옵션 B: 시설부 점검을 다시 다회차(예: 오전/오후 순회)로 재설계 — 별도 GM 결재 필요한 운영 변경(입력 UI까지 손대야 함, 07-08 결정 롤백).
2. **이상내용 표시 범위** — 서버 `이상내용`은 사우나·수영장 수치기준(FC_MEASURE_RANGES)만 자동판정한 값이고, 온수탱크·공조기·기계실·안전은 "서버도 기준 미설정 → 판정 제외"(현재 클라이언트 주석과 동일 원칙, L10755). 이 범위를 유지할지, `fc_ooc_action`(기준이탈 조치)·`fc_work`(작업사항) 같은 자유텍스트도 "이상"에 포함할지 결정 필요 — 후자는 사람이 적은 텍스트라 오탐/과탐 가능.

## 4. 프론트 변경안 (백엔드 필드 도착 후, home 카드 `buildFacilityGroupCard` 재구성)

주(主) 표시를 완료율(pct)에서 **"○ 진행 · 이상 N건"**으로 교체, 완료율은 부차 정보로 하단 이동:
```
🏭 시설부 점검
1일 회차 진행 · 이상 없음        ← 주 표시(회차+이상, 정직 표기)
  또는
1일 회차 진행 · ⚠️이상 2건 (툴팁: 사우나 온탕(a):43.2 / ...)
──────────────────────
[기존 6그룹 done/total·pct 행 유지 — 보조 정보로 축소]
```
- 이상 0건은 "이상 없음"으로 명시(침묵 금지 — 메모리 원칙 "정직 표기").
- 이상건수>0이면 이상내용 요약을 `title` 툴팁 또는 접는 줄로 노출(카드 높이 급증 방지).
- 지원부 카드(완료율 중심 유지, GM 지시가 시설부 한정)·기존 데이터 바인딩은 무변경.

## 5. 현재 상태 — ✅ 구현 완료·라이브 반영 (2026-07-14, 같은 세션)

GM 정정: "오늘도 시설 7회 점검·8회 작성중으로 뜬다 — 이미 다회차다. 그 소스를 찾아 home으로 가져와라." 재조사 결과 §1의 전제(1일 단일 회차·GAS 확장 필요)가 틀렸음을 확인:

- **진짜 소스 발견**: `시설부 체계.html`의 "오늘 N회 점검" 표시(L3805)는 `handleWeekly`가 아니라 **`action=board&key=FACILITY_CHECK_<date>`**(제출마다 `saveBoard`로 누적되는 blob, `store.submissions[]`)에서 나온다. **이 액션은 이미 배포돼 있고 이미 크로스오리진으로 호출 중**이라 GAS 변경 0으로 home에서도 그대로 재사용 가능했다.
- **이상 판정**: 사우나/수질 수치기준 초과(기존 `FACILITY_RANGES` 로직 재사용, 이번엔 오늘의 모든 제출 회차를 순회) + `fc_work`(작업사항)·`fc_ooc_action`(⚠️기준이탈 조치) 자유기록 텍스트(하루 유지값이라 최신 제출 1건만 채택, 원문 그대로 툴팁 노출) — GM 지시(둘 다 포함) 그대로 반영.
- **구현 파일**: `3. 웰페리온 가이드/wellperion_guide(main).html` — `parseFacilityBoard()` 신설 + `buildFacilityGroupCard()`를 "오늘 N회 점검·N+1회 작성중"+"이상 N건/없음" 주표시로 재구성(기존 6그룹 완료율은 부차로 축소) + `fetchBoth()`에 board fetch 1건 추가. **GAS 백엔드·완료율 집계·지원부 카드는 무변경(가산만, 회귀 0).**

# 회원 도메인 이행 설계 — 시트에서 배101까지

읽는 순서: GM님은 §1~§4까지만 읽으셔도 결정에 충분합니다. §5부터는 시토·시포용 상세입니다.

## 1. 결론 한 장

| 항목 | 결정 |
|---|---|
| 방향 | **회원등기부 + 불변 회원번호** 하나로 간다. 사람마다 평생 안 바뀌는 번호(M00001…)를 부여하고, 흩어진 7벌 원장의 모든 행을 이 번호로 꿴다 |
| 왜 | 지금 사고(저장 거부·가족 등록 불가·중복·먹통)의 뿌리가 전부 하나다 — **바뀌는 값(전화·등록일자)으로 사람을 찾는 것.** 안 바뀌는 번호 하나면 뿌리가 뽑힌다 |
| 지금 시트는 | 버리지 않는다. 번호 칸만 **덧붙인다**(기존 칸·수식·화면 그대로). 실무진 화면도 지금 것 하나 그대로 |
| 배101과는 | 이 등기부와 다섯 장부 모양이 **그대로 배101 회원 모듈의 뼈대**가 된다. 번호가 시트→AWS 이주의 열쇠 |
| 첫 조각 | **「사람 찾기」 화면** — 이름 하나 넣으면 문의부터 지금까지가 한 화면에 나온다(지금은 시트 3~6개를 사람이 뒤진다) |
| 사람 손 판정 | 급한 것은 **19건뿐**(회원 원장 중복 12 + 등록완료인데 원장에 없는 7). 나머지 1,124건 전화 충돌은 자동 분류 후 표시만 하고, 확실할 때만 합친다 |
| GM 결재 필요 | 이 문서 승인 = ①회원등기부 탭 신설(신규 생성 항목) ②배101 회원 모듈 뼈대 확정. 비용 발생 없음(배101 자체 비용은 별건·기존 결재 대기 그대로) |

검토했지만 안 고른 길(한 줄씩):
- 전화+이름 지문을 더 정교하게 고치기 — 바뀌는 칸에 의존하는 한 반드시 또 무너진다(이미 두 번 무너짐).
- 시트 4탭을 지금 한 탭으로 합치기 — 실무진 화면·수식이 탭 전제라 하루 멈출 위험. 합치는 건 배101 데이터베이스에서 한다.
- 배101 나올 때까지 시트를 안 건드리기 — 저장 막힘·대신 고쳐달라는 카톡(어제 3건·오늘 3건)이 지금 진행형이라 못 기다린다.
- 중간에 외부 데이터베이스(에어테이블 등) 끼우기 — 진실이 세 곳이 된다(약속 L01 위반).

## 2. 지금 병이 무엇인가 (요약)

| 병 | 실측 | 뿌리 |
|---|---|---|
| 저장이 막힌다 | 같은 전화에 이름 둘 이상 1,124건 → 가족은 저장 거부 (실제 사고 2인) | 전화로 사람을 찾음 |
| 저장이 또 막힌다 | 보조 지문(등록일자+전화+이름)의 등록일자를 실무진이 고치면 그 뒤 전부 실패 (실제 사고 2인) | 바뀌는 칸으로 지문을 만듦 |
| 사람이 흩어진다 | 한 사람이 원장 2벌 이상에 924명 · 회원 원장끼리 중복 12건 · 강습 문의 최대 14줄 | 상태·종목마다 행과 탭이 갈라짐 |
| 기록이 안 남는다 | 강습 등록완료 1,807건 중 등록일 기재 2건 · 멤버십 등록완료 206건 중 원장에 없는 사람 7건 | 등록 사실을 담는 장부가 없음 |
| 느리다 | 저장 왕복 21~33초 · 명단 조회 최대 83초 → 화면에 덧댄 층(로컬 버퍼 811줄 등)만 비대 | 구글 시트+웹앱의 한계(코드로 못 줄임) |

느림은 배101(AWS)로만 풀린다. **어긋남은 지금 풀 수 있고, 지금 풀어야 배101 이주도 가능하다** — 어긋난 데이터는 이주가 안 된다.

## 3. 방향 — 회원등기부와 다섯 장부

### 3-1. 사람마다 평생 번호 하나
- 새 탭 **「회원등기부」** 1개를 만든다. 한 사람 = 한 줄. 칸은 최소한만: 회원번호 · 이름 · 전화 · 관계(보호자 회원번호) · 소속법인 · 메모.
- 회원번호는 **한 번 주면 절대 안 바꾸고 재사용도 안 한다.** 전화가 바뀌어도, 이름을 고쳐도, 탭을 옮겨도 번호는 그대로다.
- 기존 7벌 원장에는 **회원번호 칸 1개만 덧붙인다.** 기존 칸·수식·화면은 손대지 않는다 → 실무진은 아무 변화를 못 느낀다.

### 3-2. 가족·아이·법인을 이렇게 담는다
| 경우 | 지금 | 새 모양 |
|---|---|---|
| 가족 공유번호 (김준수/최은정) | 저장 거부 | 사람마다 등기부 1줄씩 · 전화는 같아도 됨 |
| 아이 둘을 한 칸에 (방태오(5세)/방현오(7세)) | 이름 칸에 슬래시 | 아이 각각 1줄 + 보호자 번호로 연결 |
| 동명이인 접미 (김혜경/김혜경4) | 숫자 붙여 구분 | 번호가 구분하므로 접미 불필요(이름은 원래대로) |
| 법인 32건 | 별도 탭 | 법인도 등기부에 1줄(법인 표시) + 소속 직원은 소속법인 칸으로 연결 |

### 3-3. 최종 모양(배101) = 다섯 장부
사람 1명의 생애(문의→상담→등록→갱신→이탈→재등록)를 탭 이동 없이 담는 모양이다.

| 장부 | 한 줄 = | 지금 어디에 흩어져 있나 |
|---|---|---|
| ①사람(등기부) | 사람 한 명 | 7벌 전부의 이름·전화 칸 |
| ②등록(계약) | 계약·수강 한 건 (상태 칸 포함: 유효/종료/LOSS/대기) | 회원 원장 4벌 = 상태별로 쪼개진 같은 표 |
| ③문의 | 문의 한 건 | 멤버십문의·강습문의 2벌 |
| ④종목배정 | 사람×종목×담당자 한 건 | 유효회원의 종목 담당 10칸 · 강습 14줄 분할 |
| ⑤연락기록 | 연락 한 통 | Contact 칸 5개·contacts 칸에 눌러 담긴 텍스트 |

- 상태가 바뀌면 **②등록 행의 상태 칸만 바뀐다.** 탭 이동·행 복사·보관 행 잔류가 전부 사라진다.
- '회원구분'(멤버십/입주민/법인…)과 '등록 분류'(신규/재등록…)는 둘 다 ②등록의 칸이 된다 — 한 표에 섞인 두 축이 풀린다.
- 종목이 늘어도 ④에 행이 늘 뿐, 칸은 안 는다.
- 시트 과도기에는 ②~⑤를 안 만든다. 시트에서는 번호만 꿰고, 다섯 장부로 갈라 담는 것은 배101 데이터베이스에서 한다.

## 4. 여덟 질문에 대한 답

### 질문1. 회원 한 사람을 무엇으로 식별하나
**회원번호(불변 일련번호)다.** 전화·이름·등록일자는 전부 "바뀌는 정보"로 강등되어 검색에만 쓰고 식별에는 안 쓴다.

기존 11,153행을 번호로 꿰는 방법 — **원칙: 잘못 합치는 것보다 안 합치고 두는 게 안전하다. 병합은 나중에 해도 되지만 잘못 병합은 실고객 데이터 사고다(INC-020 교훈).**

| 구간 | 건수 | 처리 | 사람 판정 |
|---|---|---|---|
| 전화 충돌 없는 사람 | 전화 5,745개(6,869−1,124) | 자동으로 번호 부여 | 없음 |
| 전화 충돌 1,124건 | 접미숫자(김혜경4)·한 글자 오타(박초은/박초응)·슬래시 두 명·완전 다른 이름(가족) 유형별 자동 분류 | 같은 사람 "후보"로 표시만. 합치지 않고 각자 번호 부여 | 급하지 않음 — 화면에 후보 표시, 실무진이 그 사람을 만질 때 확인 버튼으로 확정 |
| **회원 원장 중복 12건** | 이름 같음 3(허나래·송의영·김혜경) + 전화만 같음 9 | 돈이 걸린 현역 데이터라 즉시 판정 | **임정은M** (시포가 12건 대조표 준비) |
| **등록완료인데 원장에 없음 7건** | 멤버십 SUC 206건 중 7 | 실제 등록 여부 확인 후 원장 기재 또는 상태 정정 | **임정은M** (시포가 7건 목록 준비) |

즉 사람이 당장 판정할 것은 **19건**이다. 자동 분류가 1,124건 중 몇 %를 후보로 묶는지는 돌려봐야 안다 — 확인 필요(시포 · 1단계에서 실측해 보고).

### 질문2. 생애를 어떤 모양으로 담나
§3-3 다섯 장부다. 바뀌는 것: **상태 변경 = 탭 이동 → 칸 수정.** 가족·아이·법인은 §3-2 표대로다.
시트 과도기에는 탭 이동이 그대로 남되, **번호가 행을 따라다니므로** 옮겨도 같은 사람임이 끊기지 않는다.

### 질문3. 종목 담당 10칸과 14줄 분할을 어떻게 푸나
- 근본 수리 = ④종목배정·⑤연락기록 장부(배101). 종목당 칸 2개가 행으로 바뀌고, 문의 1건은 문의 1행 + 배정 N행이 된다.
- 시트 과도기 = 구조는 못 고친다(폼→시트 배선이 그대로라). 대신 **「사람 찾기」 화면이 번호로 묶어 1명으로 보여준다** — 서승규 님 14줄이 "서승규 1명, 문의 1건, 종목 7개, 담당 7명"으로 보인다. 담당자가 엉뚱한 종목 강사로 보이는 신고가 이 화면에서 해소된다.
- 기존 Contact 칸의 텍스트는 배101 이주 때 ⑤연락기록에 원문 그대로 1행씩 옮긴다(유실 0).

### 질문4. 7벌을 어떤 순서로 옮기나(=번호를 꿰나)
| 순서 | 원장 | 행수 | 왜 이것부터 |
|---|---|---|---|
| 1 | 회원 원장 4벌(유효·종료·법인·LOSS보관) | 1,739 | 가장 작고, 칸이 거의 같고, 돈이 걸린 핵심 자산. 중복 12건도 여기 있다 |
| 2 | 멤버십문의 | 732 | 회원 원장과 바로 이어지는 앞 단계. SUC 7건 어긋남 정합 |
| 3 | 강습문의(성인) | 3,704 | 크고 지저분(빈 상태 1,226). 번호 체계가 1·2에서 검증된 뒤 |
| 4 | 강습문의(유소년) | 4,978 | 가장 크고 가장 지저분(빈 상태 2,260·가족 충돌 밀집). 마지막 |

**멈춰도 안전한 지점 = 매 순서의 끝.** 번호는 덧붙임이라, 어디서 멈춰도 기존 동작은 그대로다(번호 없는 행은 지금처럼 지문으로 동작).

### 질문5. 옮기는 동안 실무진은 어디서 일하나
**지금 화면 그 하나에서 계속 일한다.** 화면 주소·생김새·버튼이 안 바뀐다. 바뀌는 것은 화면 속 저장 열쇠(지문→번호)뿐이고 실무진 눈에 안 보인다. 두 곳을 동시에 볼 일이 없다.

되돌릴 지점:
| 단계 | 되돌리는 법 |
|---|---|
| 번호 칸 부여 | 칸을 무시하면 그걸로 끝(기존 지문 체계가 그대로 살아 있음). 칸 삭제도 가능 |
| 저장 열쇠 전환 | 서버 스위치 1개로 지문 방식 복귀(액션별로 켜고 끔) |
| 배101 이주 | 이주 후 2주 시트 병행 기록(읽기 전용 백업) 뒤 시트 동결 — 상세는 배101 착수 시 별도 설계 |

### 질문6. 화면 797KB에서 무엇을 버리나
**판정 기준 하나: "이 층이 덮는 병이 무엇인가."** 식별 병을 덮는 층은 번호 전환 뒤 삭제, 시트 느림을 덮는 층은 배101 이주 뒤 삭제.

| 덧댄 층 | 덮는 병 | 판정 |
|---|---|---|
| 지문 미스 복구 3중 분기 | 식별 | **3단계(열쇠 전환) 뒤 삭제** |
| 로컬 저장 버퍼 811줄 | 왕복 21~33초 | 시트 동안 유지 · 배101에서 삭제 |
| 캐시 3종 + 스냅샷 가속층 | 조회 10~83초 | 시트 동안 유지 · 배101에서 삭제 |
| 저장 실패 서버 통보(08-25 신설) | 감시(병 아님) | 유지 — 배101에서도 그대로 쓴다 |

삭제는 항상 "새 길이 1주 무사고"를 확인한 뒤 한다. 남는 것 = 조회·입력 화면 본체와 위 표의 "유지" 층.

### 질문7. 배101과 어디서 만나나
- **다섯 장부(§3-3) = 배101 회원 모듈의 데이터베이스 설계 그 자체다.** 이 문서 §6이 그 뼈대이고, 시토가 Phase 0 결재 후 이 뼈대로 만든다.
- **회원번호 = 이주 열쇠.** 시트에서 지금 부여한 번호가 AWS로 그대로 간다. 이주 스크립트는 "번호 있는 행을 옮기고 행수를 대조"만 하면 된다 — 지금 번호를 꿰는 작업이 곧 이주 준비다.
- 멀티테넌트(여러 회사): **회사번호 칸 1개만 처음부터 넣는다**(웰페리온=1번). 칸 하나 비용으로 나중의 전면 재작업을 면한다. 회사별 화면·권한은 배101 뒷단계 일이고 지금 안 만든다.
- 브로제이 연동(①연동→②대체)도 회원번호가 맞물림 열쇠가 된다 — 연동 규격은 확인 필요(시토 · Phase 0 이후).
- 배101 전까지 버티는 것 = 시트+번호 체계(1~4단계). 이것으로 저장 사고·중복·먹통 중 "어긋남" 계열은 멎고, "느림" 계열만 배101을 기다린다.

### 질문8. 첫 조각은 무엇인가
**「사람 찾기」 화면.** 기존 화면 안의 탭 하나로 넣는다(새 페이지 안 만듦 — 약속 L21).
- 이름(또는 전화·번호) 하나 넣으면 → 등기부 1줄 + 그 번호가 꿰인 모든 행(문의·상담·등록·상태·담당·연락기록)이 시간순 한 화면.
- 읽기 전용으로 시작한다 — 쓰기가 없으니 데이터 사고 위험 0. 그래서 열쇠 전환(3단계)보다 먼저 낼 수 있다.
- 필요한 것 = 1단계(등기부+회원 4벌 번호) 완료 + 조회 액션 1개 + 화면 탭 1개. 문의 원장은 2·4단계가 끝나는 대로 이 화면에 합류한다.

**검증(숫자로 센다):**

|---|---|---|
| 1 | 표본 10명 검색 → 나온 행수를 원장 수동 대조 | 불일치 0 |
| 2 | 서승규 님 검색 | 1명으로 나오고 14줄이 문의 1건·종목 7개로 접혀 보임 |

## 6. 개발자 상세 (시토·시포용)

### 6-1. 회원번호 규격
- 형식 `M00001`(M+5자리, 부여 순번). 법인도 같은 체계(등기부에 종류 칸으로 구분).
- 재사용·재부여 금지. 삭제 대신 등기부에 상태 표시(병합됨→대표번호 기입).
- 병합은 "부번호→대표번호 포인터"로만 한다. 행을 지우지 않는다(INC-020 원칙).

### 6-2. 등기부 탭 칸
`회원번호 · 이름 · 전화(정규화) · 종류(개인/법인) · 보호자회원번호 · 소속법인회원번호 · 병합대표번호 · 생성일 · 메모`

### 6-3. 시트 과도기 배선 (Survey.js)
- 7벌 각 탭 끝에 `회원번호` 칸 1개 추가. 기존 칸 위치 불변 — 헤더명 기반 접근이라 안전하나, 시트에 붙은 외부 수식(IMPORTRANGE 등) 영향은 확인 필요(시포 · 0단계에서 목록화).
- 행 지목 우선순위: `회원번호 → (없으면) 기존 rowKey 지문 → (없으면) _findRowByPhone_`(Survey.js:150). 번호 매칭이면 지문·전화 검사 생략 → 1,124건 충돌 구간과 등록일자 수정이 저장을 더는 못 막는다.
- 전환 대상 쓰기 액션: `member_active_update` · `member_inquiry_update` · `lesson_inquiry_update` · `member_archive_restore` · `member_registered_add/remove` · `member_owner_save` · `member_hold_*`. 액션별 플래그로 켜고 끈다(즉시 롤백).
- 신규 유입(폼·intake_submit)은 저장 시점에 등기부 조회→없으면 번호 신규 발급.
- 「사람 찾기」 = 읽기 액션 1개 신설(`member_person_view` — 번호로 7벌 횡단 조회, 캐시 재사용). 대신 은퇴 예정 1개 지정으로 net-zero(후보: 지문 복구 경로 · 3단계에서 확정).

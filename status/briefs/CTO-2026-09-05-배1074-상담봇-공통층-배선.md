## 배선 3가지

| # | 무엇 | 어떻게 |
|---|---|---|
| ① 공통부가 shared 3파일을 읽는다 | system 프롬프트에 `concept_presets.json`(프로필 `identity.concept_preset` 로 선택된 1개 — 지금은 3업체 다 미선택이라 no-op, 나중에 시보가 지정하면 자동 반영) · `guards_common.json`(전부 · 규칙 문장으로) · `question_types.json`(전부 · 유형+답 뼈대) |
| ② `_forbidden_hit` = 공통+업체 phrases 합집합 | `guards_common.json` 37개 phrases + 테넌트 `guards.phrases`(지금 3업체 다 0개 — 필드는 있음) + 계좌번호형 정규식(`\d{2,6}-\d{2,6}(-\d{2,6})?`). 의료 안전목록(`MEDICAL_WORDS`)은 guards_common 이 아직 다 못 덮어(처방·질환·수술 등 누락) 유지 |
| ③ chat_log 에 type_id·needs_facts | 질문마다 `question_types.json` 유형 매칭(2-gram 겹침 · FAQ 매칭과 같은 방식이되 임계를 완화 — 이유는 아래) + 정본에 필요한 칸이 비어 있으면 `needs_facts`. **답변 성공 여부와 무관하게 항상 기록**(모델이 둘러 답해도 "이 칸이 비었다"는 신호는 똑같이 값지다) |

**never_here 지킴**: shared 파일은 코드가 **읽기만** 한다 — 쓰는 코드 0(grep 확인). 사실 값·개인정보는 프롬프트에 넣을 때도 `[업체 정본]`(테넌트 json) 쪽에서만 오고 shared 3파일 쪽은 규칙 문장·유형 텍스트뿐.

## 설계와 다르게 만든 것 1개(이유 있음)

`_match_question_type`은 `_best_match`(FAQ 매칭)를 그대로 재사용하려 했으나 실측에서 실패 — `_best_match`는 "정규화하면 2자 이하"인 질문을 안전을 위해 무조건 미매칭 처리하는데, "주차 되나요"·"환불 되나요" 처럼 흔한 질문이 정규화(조사·어미 제거)하면 정확히 2자("주차"·"환불")로 줄어 전부 미매칭이 났다. 유형 태깅은 답 선택(FAQ)과 달리 오분류 비용이 낮아(잘못 붙어도 안전에 영향 없음 — 그냥 통계 라벨) 그 안전장치를 빼고 교집합 1개부터 인정하는 별도의 작은 함수로 새로 짰다. FAQ `_best_match`는 그대로(안전장치 유지).


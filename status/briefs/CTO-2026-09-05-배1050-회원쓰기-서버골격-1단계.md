# 배1050 — 회원 쓰기 서버 원장 1단계(member_owner_save) 라이브

작성 AI 시토 · 2026-09-05 · 시포 스펙(status/briefs/CPO-2026-09-05-회원쓰기7종-서버원장-스펙.md) §2-2 이행

## 1. 라우트 규격

`POST /api/members/write` (신설 · `server/erp_api/api_members_write.py` · app.py 자동등록, 손 안 댐)

- 로그인 뒤 관문(nginx `/api/` auth_request 통과 · `/api/write` 와 같은 인증)
- body: `{action:"member_owner_save", field, phone, value, staff}`
- 1단계는 `member_owner_save` 만 처리. 나머지 6종(`member_active_update` 등)은 **501** + "아직 GAS 경로(/api/write)를 쓰세요" 안내.
- 처리 순서: ①검증(화이트리스트 5칸 · 전화 필수 · GAS mosAllowed 그대로) ②서버 원장(`members.owner_pt/golf/pl/squash/swim`) 갱신 + `member_change_log` 이력 1줄, 한 트랜잭션(멱등 — 값 같으면 이력 없이 ok) ③write-through: 기존 GAS(FUNNEL_EXEC_URL)로 원본 body 그대로 포워드(`api_write._gas_forward` 재사용) — 실패해도 서버 저장은 이미 끝나 있고 응답 `gas_status`(ok/gas-error/forward-failed)로만 알린다.
- 응답: `{ok, phone, field, value, rowIndex(=member_no), _source:"server", gas_status}`

## 2. 스키마 변경 (`server/common/schema.sql`)

- `members` 에 `owner_pt/owner_golf/owner_pl/owner_squash/owner_swim` TEXT 5칸 추가 + 1회성 백업(data JSON → 새 컬럼, `WHERE owner_* IS NULL` 라 멱등).
- `sync_members.py` 의 INSERT 열 목록엔 이 5칸이 없다(의도) — 5분 거울 갱신이 서버가 쓴 값을 되덮지 않는다.
- `member_change_log` 신설(9칸: 시각·직원·회원번호·회원명·연락처가림·항목·이전값·새값·화면 — GAS 8칸 + member_no).
- 배포 서버(15.164.151.105)에 `db.init_schema()` 로 적용 완료.

## 3. 3일 무결 대조 (`reconcile_dual_write.py`)

- `reconcile_member_owner_writes()` 신설 — write_log(action=member_owner_save·gas_status=ok) 의 (member_no, field, value) 를 그 시각 **이후** 처음 돈 `members.data` JSON 같은 칸 값과 대조. 아직 안 돈 건 mismatch.
- `main()` 출력 `forms.member_owner_save` 로 얹힘 — 기존 `streak_ok_days` 가 그대로 먹는다(새 cron 없음 · 06:10 KST 기존 것 재사용).
- 새 cron 없음. write_log 페이로드에 `_member_no` 를 서버가 추가로 실어 대조 열쇠로 쓴다(화면이 보낸 값 아님).

## 5. 시포에게 되묻는 질문

1. **전화 첫 매칭 순서** — GAS 는 "시트 맨 위 행"이 첫 매칭인데 서버엔 행 순서가 없어 **member_no 오름차순**으로 대신했다. 실질적으로 문제되는 사례(가족 공유번호로 여러 유효회원)가 있으면 알려달라 — 그때만 정렬 기준을 다시 본다.
2. **응답 `rowIndex`** — 스펙 응답 계약을 그대로 지키려 시트 행번호 대신 **회원번호(member_no)** 를 담았다. membership.html 화면이 `rowIndex` 값을 실제로 쓰는 로직이 있는지(재조회 등) 확인 필요 — 있으면 그 로직도 회원번호 기준으로 같이 손봐야 한다.
3. **member_change_log 조회 화면** — GAS `회원변경이력` 탭처럼 사람이 보는 화면이 필요한지, 필요하면 어느 화면에 붙일지(멤버십 상세 모달 등) 결정 필요.

## 6. 2~7단계 순서 (시포 스펙 §3 그대로)

1. ✅ member_owner_save (이번 배)
2. member_hold_transition — 1칸(휴회접수상태) · 회원번호 지목으로 fail-open 제거
3. member_active_update — rowIndex+rowKey → member_no 변환층이 핵심(가장 큰 작업)
4. member_hold_approve — 2원장·증분 · 3단계 변환층 재사용 · 접수 상태 재검사 가드 추가
5. member_registered_add — 신규 행·서버 채번
6. member_archive_restore — scope 전환 + 칸 인계
7. member_registered_remove — 하드 삭제 → soft-delete + 이력 보존

각 단계 전환 전 3일 연속 mismatch 0 게이트(같은 `reconcile_dual_write.py`) 통과 확인 — 전환 판단은 사람.

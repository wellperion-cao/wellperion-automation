## 1장. 회원 미러 — 시트 → 서버 `members` 표 (읽기 전용 · 5분 동기화)

### 원천 (시트·GAS 무변경)
| 탭 | 실측 행수(2026-08-26) | GAS 조회 액션 | 비고 |
|---|---|---|---|
| 유효회원 | 994 (종료회원 208 포함 시 1,202) | `member_active_list` scope=valid / scope=ended | 종료회원은 별도 탭이 아니라 같은 탭 안에서 잔여일·LOSS 태그로 갈린다 |
| 법인 현황 | 32 | `member_active_list` scope=corp | 탭 이름에 공백 — gid 1612064257 이 정본 |
| LOSS보관 | 505 | `member_active_list` scope=archive | |

- 시트 파일 = 회원 DB `12AWcAlg…`(MEMBER_SPREADSHEET_ID). 회원등기부 탭(회원번호 M00001~M01737)은 2026-08-26 부여 완료 — 각 탭 맨 뒤 「회원번호」 칸.
- **동기화 = 문의 미러와 같은 규칙**: 조회 성공 + 행 있음일 때만 그 scope 를 통째로 갈아끼운다. 실패하면 옛 미러를 그대로 둔다(빈 값으로 덮지 않는다).

### 표 정의 (`members`)
| 칸 | 원천 칸 | 뜻 |
|---|---|---|
| member_no (PK) | 회원번호 | M00001… 평생 불변. **없는 행은 미러에 넣지 않고 `sync_meta.unnumbered` 에 건수만 적는다** — 번호 없는 사람이 몰래 들어오면 열쇠가 다시 전화로 돌아간다 |
| scope | (조회 scope) | valid / ended / corp / archive |
| name · phone | 회원명 · 휴대폰 번호 | 전화는 숫자만 11자리로 정규화 |
| kind · kind2 | 회원 구분 · 세부 구분(법인만) | |
| program | 수강반종목명 | |
| reg_class · reg_seq | 등록 분류 · 등록 회차 | 신규/재등록/L재등록 판정의 원료 — **판정은 GAS `_isNewRegistration_` 한 곳**, 서버에서 다시 안 한다 |
| reg_date · start_date · end_date · loss_date | 등록·시작·종료·LOSS 일자 | YYYY-MM-DD |
| remain_days | 잔여일 | 시트 수식값 그대로(원천이 브로제이 → 배908 붙으면 그쪽으로 교체) |
| owner | 담당자 | |
| data | (행 전체 JSON) | 나머지 칸 전부 — 화면이 아직 안 쓰는 칸을 잃지 않게 |
| synced_at | | KST |

- 인덱스: `(scope, end_date)` · `(phone)` · `(name)`.
- 개인정보 범위: 이름·전화·주소가 들어간다. **API 는 로그인 쿠키 뒤에서만**(nginx auth_request — 문의 미러와 동일). 공개 페이지에서 부르지 않는다.

### API (문의 미러와 같은 모양)
| 경로 | 무엇 |
|---|---|
| `GET /api/members?scope=valid&q=이름또는전화&limit=` | 목록 · q 는 이름 부분일치 또는 전화 뒷자리 |
| `GET /api/members/{member_no}` | 한 사람 — 회원 행 + **같은 전화·이름의 문의**(`inquiries` 표 조인) = 「사람 찾기」 첫 조각이 서버에서 나온다 |
| `GET /api/members/summary` | 유효·종료·법인·LOSS 건수 + last_sync + unnumbered 건수 — 화면 자체점검용 |

### 합격선 (배 801 첫 조각 검증 기준 그대로)
1. 미러 건수 = 라이브 GAS 건수(허용 오차 0 · 동기화 직후).
2. `/api/members/{M번호}` 에 이름 하나 넣으면 문의부터 지금까지 한 화면 — 서승규 님 14줄이 1명으로 접혀 보인다.
3. unnumbered = 0. 0 이 아니면 등기부 재부여(`member_registry_build`, 멱등)를 먼저 돌린다.

## 2장. 홈페이지 가입 회원 ↔ 회원번호 매칭 규칙

시토 로그인 관문 = 가입 신청 → GM 승인 → 로그인. 여기에 **회원번호 연결**을 한 단계 얹는다. 규칙은 셋뿐이다.

| 경우 | 판정 | 처리 |
|---|---|---|
| 가입 폼의 **전화(정규화) + 이름**이 미러에서 **정확히 1명** | 확정 | 그 member_no 를 계정에 연결. GM 승인 화면에 「회원 M00123 · 유효회원 · 종료 2026-12-31」 한 줄 표시 |
| 전화만 같고 이름이 다르거나, 2명 이상 | 후보 | **자동 연결 금지.** 계정은 `member_no=NULL` 로 두고 「후보 N명」 표시 → 임정은M 이 회원 화면에서 고른다(설계문서 원칙: 잘못 병합이 미연결보다 위험 — 가족 공유번호·회원권 양도가 실재 21건) |
| 미러에 없음 | 신규 | `member_no=NULL` · 「회원 원장에 없음」 표시. 회원이 되는 순간(등록) 시트에 행이 생기고 다음 등기부 부여 때 번호를 받는다 — 그때 연결 |

- 매칭은 **미러(서버)에서만** 한다. 가입 시점에 GAS 를 부르지 않는다(7초 응답·캐시 문제를 관문에 들이지 않는다).
- 연결 기록 = `accounts.member_no` 칸 하나 + 누가·언제 연결했는지(`linked_by`, `linked_at`). 되돌리기 = 그 칸 비우기.
- 회원 아닌 실무진 계정은 처음부터 이 단계를 건너뛴다(역할 staff/admin).

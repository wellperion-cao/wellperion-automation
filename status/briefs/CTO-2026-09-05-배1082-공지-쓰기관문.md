# 공지서식 저장·삭제 쓰기 관문 경유 (배1082)

원인 — `coo/notice/notice_template.html`의 공지 저장(`notice_save`)·삭제(`notice_delete`)가 업무·결재 GAS
(`NOTICE_API_URL` = `TODO_GAS_URL`과 같은 프로젝트)로 직행해, 서버 `write_log` 이중기록이 안 남았다.
화면은 이미 `window.erpTodoCall(...)`로 바뀌어 있었지만, 관문 통과 조건(`erp_write.js` `WRITE` 정규식·서버
`api_write.py` `_gas_key` 목적지 표) 둘 다에 `notice_save`·`notice_delete`가 없어 매번 관문을 우회했다.

## 조치

- `server/erp_api/api_write.py` `_gas_key`: `notice_save`·`notice_delete` → `TODO_GAS_URL` 추가.
  거울 없음 — `MIRROR_SYNC`에는 미등록(공지서식은 시트 자체가 원본이라 별도 거울이 없다).
  자체점검(`__main__`)에 `_gas_key("notice_save"/"notice_delete") == "TODO_GAS_URL"` +
  `MIRROR_SYNC`에 안 들어있는지 확인하는 assert 2줄 추가.
- `3. 웰페리온 가이드/_assets/erp_write.js` `WRITE` 정규식에 `notice_(save|delete)` 추가 — 이제 ERP
  도메인에서 이 두 액션은 `/api/write`로 먼저 간다.
- 큰 HTML 본문 제한: nginx `client_max_body_size 10m`(`api.nginx.conf`) — 사진 base64(`staff_feedback_photo`)
  기준이라 공지 서식 본문(텍스트 HTML)에는 넉넉하다. 별도 상향 불필요.
- GET 파라미터 우려(`notice_delete`가 원래 GET) — 실제로는 문제 없음. TODO GAS 프로젝트의 `doPost`가
  `e.postData.contents`를 JSON으로 파싱해 `notice_`로 시작하는 액션을 전부 `_processNoticeAction(body)`로
  넘긴다(`doGet`·`doPost` 둘 다 같은 처리, 코드 확인). 관문은 항상 POST(JSON 본문)로 전달하므로 그대로 맞물린다.

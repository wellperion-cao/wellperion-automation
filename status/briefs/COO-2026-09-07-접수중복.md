## 1. RECEPTION-148 (수영장 여자사우나 층계 미끄럼방지 테이프)
- 서버 DB(reception_items) 조회 결과 148은 **단일 레코드**다. 같은 내용의 중복 티켓은 없다.
- status=완료, 그러나 memo: "9월 13일날 휴관일날 교체 할 예정입니다 — 근데 이건 누가 붙여도 똑같은 작업 방식입니다."
- **원인 = ②(완료 처리했지만 실제로 안 고쳐짐).** 접수를 "완료" 처리해 놓고 실제 항구 조치는 9/13 휴관일로 미뤄뒀다. GM이 현장에서 다시 본 것은 새 접수가 아니라 안 고쳐진 채로 남은 같은 문제다.
- 같은 부위(여자사우나 미끄럼·물기) 이슈가 RECEPTION-58(7/22)·64(7/25)에도 있었다 — 매번 임시 조치(탕청소 업체 컨택, 테이프 재부착)로 닫혔고 근본 조치(비접착식 항구 대책)가 없어 반복된다.
- **조치 필요: 9/13 이후 실제 시공 여부를 시설부가 확인하고, 임시방편이 아닌 항구 대책(미끄럼방지 타일/에폭시 등)을 검토** — 이 부분은 시토(CTO)/시설팀 소관이라 이 배에서 시공은 하지 않는다.

## 3. 접수 순간 중복 알림 — 설계 (화면 잠김 status/reception_freeze.json → 코드 미적용, 설계만)
접수하는 사람이 접수 순간에 "이미 접수돼 있다"를 알게 하는 것이 근본 대책.

**동작:** 공개 접수 폼(`3. 웰페리온 가이드/cmo/survey/wp_inquiry_form.html` 계열 · 종합접수처 폼)에서 제목/본문 입력 후 제출 버튼을 누르기 **직전**, 서버에 유사 검사를 1회 조회 →
- 최근 60일 내 같은 부서(dept, loc→dept 매핑 결과) + 같은 카테고리로, 입력한 본문과 유사도 ≥0.7(또는 핵심 명사 3개 이상 일치)인 건이 있으면
- `"같은 내용이 이미 접수돼 있습니다 (RECEPTION-148 · 9/2 접수 · 처리중)"` 배너를 보여주고 **[그래도 접수] / [취소]** 두 버튼 → 막지 않고 알리기만 한다.
- 서버 응답이 없거나(타임아웃) 조회 실패 시 배너 없이 그냥 제출 진행(제출 자체를 절대 막지 않음).

**필요한 서버 조회 (현재 없음 → 시토에게 배로 넘김):**
- `GET/POST /api/reception/similar` — 입력: `{content, category, dept}` / 출력: `{ok, matches:[{regId, createdAt, status, contentPreview}]}` (최근 60일, 같은 category+dept, difflib 유사도 ≥0.7 상위 3건)
- reception_items가 이미 서버 DB에 있으니 새 테이블 불필요 — SELECT 후 파이썬 difflib 로 즉석 계산(ponytail: 데이터량 적어 인덱싱 불필요, 건수 늘면 사전 정규화 컬럼 추가 검토).

**화면 배선(잠금 해제 후 COO가 작업):** 접수 폼 submit 핸들러에서 fetch 한 번 추가, 응답 matches 있으면 confirm 배너 렌더 후 계속 진행.

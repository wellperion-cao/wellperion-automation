**임대(rentbiz_\*) 쓰기 액션은 저장소 전체(화면·`.deploy-funnel*`·서버)에 하나도 없다.** 목록·통계 두 개뿐이고 둘 다 읽기다 — 열 문이 없다. 억지로 액션을 만들지 않았다.

## 원인 — 표에 있던 것도 두 곳이 틀려 있었다

`_gas_key`(서버 목적지 판정표)에는 이미 이 6개 액션이 전부 올라와 있었다(배 961 · 2026-09-03). 그런데 **화면이 실제로 부르는 GAS 주소와 대조하니 둘이 틀려 있었다**:

- `product_plan_save`/`product_plan_delete`가 `FUNNEL_EXEC_URL`로 등록돼 있었는데, 화면(`상품기획.html`)의 실제 목적지는 `TODO_API_URL` — 서버 `TODO_GAS_URL` 값과 동일한 업무·결재 GAS 프로젝트다. 관문을 그대로 열었으면 상품기획 저장·삭제가 엉뚱한 GAS(오누띠·피드백 쓰는 프로젝트)로 갔을 것.
- `staff_feedback_photo`도 `FUNNEL_EXEC_URL`로 등록돼 있었는데, 화면의 실제 목적지(`FB_PHOTO_URL`)는 다섯 서버 GAS 키(`RECEPTION_EXEC_URL`·`TODO_GAS_URL`·`CHECK_GAS_URL`·`SCHEDULE_GAS_URL`·`PROC_GAS_URL`·`FUNNEL_EXEC_URL`) 어디에도 없는 **별도 세 번째 프로젝트**(콘텐츠 접수 재사용)다.

두 오배선은 지금까지 사고로 안 터졌다 — 클라이언트 쪽에 이 여섯 액션을 관문(`/api/write`)으로 보내는 코드가 **하나도 없어서**(전부 GAS 직접 `fetch`) 서버 표의 오류가 실행된 적이 없었다. 이번에 관문을 열려고 대조하다 발견.

## 조치

- `server/erp_api/api_write.py` `_gas_key`: `product_plan_save`/`product_plan_delete`를 `FUNNEL_EXEC_URL`에서 빼서 `TODO_GAS_URL`로 정정(`todo_`/`approval_rep_`/`notice_` 옆에 추가). `staff_feedback_photo`는 `_FUNNEL_GAS_ACTIONS`에서 제거 — 목적지가 없으면 관문이 `unknown-action(400)`을 돌려주고 화면은 종전 GAS 직접 경로로 그대로 폴백한다(저장은 되고 서버 이중기록만 안 남는다 · 새 env 키가 생기기 전까지 목적지를 지어내지 않는다).
  자체점검(`__main__`)에 두 정정 모두 assert 추가, 오류 재발 방지.
- `3. 웰페리온 가이드/_assets/erp_write.js`:
  - `WRITE` 정규식(→`erpTodoCall`)에 `product_plan_(save|delete)` 추가 — 실제 목적지가 업무 GAS라 기존 헬퍼를 그대로 재사용.
  - 새 헬퍼 `erpFunnelCall(gasUrl, params)` + `FUNNEL_WRITE` 정규식(`ohnutti_status_update`·`staff_feedback_submit`) 추가 — `erpProcCall`과 같은 모양(파싱된 객체 반환, 실패 시 GAS 폴백).
  - `staff_feedback_photo`는 어느 정규식에도 안 넣었다(목적지 없음 — 위와 같은 이유).

## 화면 배선 — cpo 도메인이라 손대지 않음(회신 필요)

시포 소유 화면 4개, 전부 `_assets/erp_write.js` 스크립트 태그조차 없다. 필요한 두 줄(경로는 두 화면 모두 `../../_assets/erp_write.js` — `coo/notice/notice_template.html`과 같은 깊이):

1. **오넛티_접수현황.html · wp_ohnutty_status_block.html** — `<script src="../../_assets/erp_write.js"></script>` 추가 후, `saveStatus()`의
   `fetch(GAS_URL,{...}).then(r=>r.json()).then(d=>{...})` 를
   `(window.erpFunnelCall?erpFunnelCall(GAS_URL,{action:'ohnutti_status_update',code:window.WELP_GATE_PW,id:id,status:newVal}):fetch(...).then(r=>r.json())).then(d=>{...})` 로.
2. **실무진피드백.html** — 같은 스크립트 태그 추가 후, `staff_feedback_submit` 부분의
   `fetch(FB_GAS_URL,{...}).then(r=>r.json())` 를 `(window.erpFunnelCall?erpFunnelCall(FB_GAS_URL,payload):fetch(FB_GAS_URL,{...}).then(r=>r.json()))` 로.
   `staff_feedback_photo`는 그대로 둔다(관문 미등록).
3. **상품기획.html** — 같은 스크립트 태그 추가 후, `_todoPost()` 내부 `fetch(TODO_API_URL,...)`를
   `(window.erpTodoCall?erpTodoCall(TODO_API_URL,payload):fetch(TODO_API_URL,...))`로.

## 실측

- 배포: `server/erp_api/api_write.py`만 scp → `/srv/erp/api/api_write.py`, 서버에서 `python3 api_write.py` 자체점검 통과 → `sudo systemctl restart erp-api` → active.
- 서버 내부(`127.0.0.1:8001`)에 `X-Erp-User` 헤더로 관문 직접 호출:
  - `staff_feedback_photo` → `{"ok":false,"error":"unknown-action"}` — 정정 확인(수정 전엔 잘못된 GAS로 샜을 자리, 이제 400으로 안전하게 막힘).
  - `staff_feedback_submit`(content=`[테스트] 배1039 폼류4종 쓰기관문 점검`) → `{"ok":true,"test":true,"id":114}` — 테스트 마커가 잡혀 `gas_status='test'`로만 원장에 남고 GAS로는 안 나감(저장 흔적 없음).
  - `ohnutti_status_update`(잘못된 접속코드) → `{"ok":false,"error":"접속코드가 올바르지 않습니다."}` — 관문→GAS 왕복 자체는 확인, 실데이터는 코드 게이트에서 막혀 안 건드림.
  - `product_plan_save`(id=`PP-CTO-PROBE-1039`, 구분=`_테스트`) → `{"ok":true,"id":"PP-CTO-PROBE-1039"}` → 즉시 `product_plan_delete`(같은 id) → `{"ok":true,...}` → `product_plan_list` 재조회로 흔적 0건 확인. 목적지가 실제로 `TODO_GAS_URL`(업무 GAS)로 정확히 갔다는 뜻 — 정정 전이었다면 이 저장이 오누띠/피드백 GAS로 새서 상품기획 시트엔 아예 안 남았을 것.

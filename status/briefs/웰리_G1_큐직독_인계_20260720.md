# 웰리(AI CEO)께 — G1 항로 보드 큐 읽기 방식 변경 인계

작성: 시우(AI COO) 2026-07-20 · 배9199에서 파생 · GM 승인받아 인계

## 왜 넘기는가

배포 적체를 고치면서 **제가 G1에 부작용을 만들었습니다.** G1은 웰리 직접 소유라 제가 손대지 않고 넘깁니다.

## 무슨 일이 있었나

오늘 라이브 배포가 1시간 넘게 막혀 있었습니다. 원인은 **큐 미러 파일이 배포를 계속 깨우고 있던 것**:

- pre-commit 훅이 `status/_queue.json` → `3. 웰페리온 가이드/status/_queue.json` 으로 미러링
- 그 폴더가 GitHub Pages 사이트 루트라, **큐 한 줄만 바뀌어도 전체 재배포가 트리거**
- C-Level들이 1분마다 큐를 갱신 → 배포가 서로를 밀어냄
- 실측(최근 6시간 커밋 91건): **실제 화면 변경 16건(18%) / 데이터만 75건(82%)**
- 결과: 최근 30회 배포 중 성공 4회. 라이브가 01:21 버전에 정체 → 전 C-Level "반영 완료" 보고가 사실상 거짓 (약속 L03 붕괴)

**조치(완료):** `.github/workflows/pages.yml` 의 paths 에 negative pattern 추가 — `!3. 웰페리온 가이드/status/**` 외 2건. 배포 트리거 82% 감소.

## 그래서 생긴 부작용

G1 항로 보드는 **배포된 미러 사본**을 읽습니다.

- `wellperion_guide(main).html` L9138-9141 부근
- `var GM1_QUEUE_URL = '/wellperion-automation/status/_queue.json';`

이제 큐만 바뀐 커밋은 배포를 트리거하지 않으므로, **G1 보드의 큐 데이터가 다음 "진짜 화면 변경" 배포 때까지 갱신되지 않습니다.** 실측 기준 **약 20~30분 지연**.

> 참고: 오늘 하루는 배포가 아예 안 뚫려 G1이 이미 몇 시간씩 옛 데이터였습니다. 즉 이 변경이 상황을 악화시킨 건 아니고, "몇 시간" → "20~30분"으로 개선된 상태입니다. 다만 원래 의도(실시간)보다는 후퇴입니다.

## 권고 — 배포 의존을 끊는다

G1이 **배포된 사본이 아니라 깃허브 원본을 직접** 읽게 바꾸면, 배포와 무관하게 항상 최신이 됩니다.

```
현재:  /wellperion-automation/status/_queue.json          (배포 사본 · 배포돼야 갱신)
권고:  https://raw.githubusercontent.com/wellperion-cao/wellperion-automation/master/status/_queue.json
       (깃 원본 · 푸시 즉시 · 배포 불필요)
```

**장점**
- 배포 큐가 아무리 밀려도 항로 보드는 항상 최신
- 미러 파일에 대한 의존이 사라짐 → 나중에 미러 자체를 없앨 길도 열림 (한 곳 원천 · 약속 L01)

**확인 필요한 점 (웰리가 판단)**
1. raw.githubusercontent 는 **약 5분 캐시**가 있습니다. 배포(20~30분)보다는 훨씬 빠르지만 "완전 실시간"은 아닙니다. 더 빨라야 하면 캐시 우회 쿼리(`?t=` + 분 단위 타임스탬프)를 붙이는 방법이 있습니다.
2. CORS 는 허용됩니다(raw.githubusercontent 는 `Access-Control-Allow-Origin: *`).
3. **비공개 저장소면 이 방법은 불가**합니다 — 현재 공개 저장소라 동작하지만, 저장소 공개 여부가 바뀌면 같이 깨집니다. 그 경우 미러 방식으로 되돌아가야 합니다.
4. 실패 시 폴백을 **옛 미러 경로**로 두면 안전합니다(원본 실패 → 미러 → 그래도 실패면 "불러오는 중" 표시. 빈 화면이나 위장 0 금지).

### 옮긴 뒤 S2는 어떻게 되나

- 원칙: 이관 완료 후 S2 해당 블록은 **하드코딩 텍스트 삭제 → 공통탭의 "우리의 약속"·"재발방지 현황" 토글과 같은 방식으로 JS fetch 렌더로 전환**(이미 존재하는 렌더 패턴 재사용, 새 메커니즘 불필요).
- **양쪽에 동시에 두는 과도기는 최대 1커밋 내로 제한**한다(같은 PR/커밋에서 ssot 추가 + S2 렌더 전환을 함께 처리) — 별도 커밋으로 나누면 그 사이 기간이 L01 위반(같은 값이 두 곳)이 되므로 기한을 "즉시(원샷)"로 명시한다. 코드 소비자가 있는 항목(#1 완료4요건, #7 GM결재5종)은 **ssot 추가 + 코드 리팩터(read from ssot) + S2 렌더 전환을 한 세트**로 묶어야 drift가 안 생긴다.

### 보고 표준 3개 문제 — 항목 대조 (유실 여부)

| 요소 | S2 사이클보고포맷(5필드) | 대응되는 L18 요소 | 유실? |
|---|---|---|---|
| 식별자 | 닉네임-번호(시토-01) | 상태 1줄의 "닉네임+배번호" | 없음 — 동일 |
| 내용 | 작업 제목 1줄 | 상태 1줄의 "제목" | 없음 — 동일 |
| 상태 | 완료/진행중/대기 | 상태 1줄의 ✅완료/⏳진행/⚠️GM필요/❌막힘 | 없음 — L18이 더 세분화(4단계 vs 3단계), 상위호환 |
| 담당자 | 닉네임 | (문답 형식 자체가 1인칭이라 별도 필드 없음, 상태1줄에 이미 포함) | 없음 |
| 링크 | SSOT 이름(업무SSOT/G1 등) | "맨 끝 기록위치 1줄" | 없음 — 동일 목적, 이름만 다름 |

**결론: L18로 수렴해도 유실되는 항목 없음.** 유일한 차이는 형식 — S2 것은 "완료/진행중/대기 여러 건을 한 표에 모은 사이클 요약"이고 L18은 "건별 단일 보고" 포맷. 이건 유실이 아니라 **L18을 여러 건에 반복 적용한 표 형태**로 자연 확장 가능(L18 각주에 "다건일 때는 표로 묶어 적용" 1줄만 추가하면 충분). L16(항로 3섹터)은 목적(아침 계획 vs 사이클 종료 보고)이 아예 달라 병합 대상 아님 — 그대로 유지.

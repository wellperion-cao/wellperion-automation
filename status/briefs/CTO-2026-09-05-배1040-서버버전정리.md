**캐시 4표는 애초에 "이력"이 없다.** sales_cache·funnel_cache·misc_cache·board_cache 는 PRIMARY KEY
가 집계 키(gas/action/params 또는 key) 자체 — sync_*.py 전부 `INSERT ... ON CONFLICT DO UPDATE`
업서트라 키당 항상 1행, DB 제약상 중복 이력 행이 생길 수 없다(실측: 4표 전부 dup-key-groups=0).
그래서 이 4표는 지운 것이 없다 — 존재하지 않는 문제를 치우는 코드는 만들지 않았다.

**/srv/erp/backup** 은 DB 백업(그건 erp-pg-backup.sh → S3 `wellperion-erp-backup`, 30일 수명주기로
이미 별도 관리 중 · 안 건드림)이 아니라 ad-hoc 덤프 폴더. 실측 결과 파일이 오늘자
`dummy_purge_20260905_145126.json`(13,571B) 1개뿐 — 접두사별 최신 2개 유지 기준에 이미 들어가
삭제 대상 0개.

## 사람 원본 중복 검사 (members·inquiries)

- members(1,746행): 전화+등록일 동일 그룹 4건 발견 → 이름 대조 결과 **전부 다른 사람**(가족이 같은
  전화로 같이 등록 — 예: 이민재/이지혜5, 임세영/임승준, Maria Campero/Oscar Garcia Chacon). 전화+
  이름+등록일 3중 일치로 다시 걸러보면 그룹 0건.
- inquiries(2,553행): 전화+접수시각 동일 그룹 1건 발견 → 이름이 다름(조이진/조온동, 유소년강습 형제
  동시접수) → 진짜 중복 아님. 전화+이름+시각 3중 일치 그룹 0건.
- **진짜 중복 후보 = 0건.** 시포 배 미발행(지시 §4: 0건이면 문서 표기로 종결).

## prune_versions.py (신설 · 배1040)

- 위치: `server/erp_api/prune_versions.py`(저장소) → `/srv/erp/api/prune_versions.py`(배포).
- 동작: `/srv/erp/backup` 파일을 접두사(파일명에서 뒤 `_YYYYMMDD_HHMMSS` 제거)별로 묶어 최신 2개만
  남기고 나머지 삭제 — 삭제 전 `/srv/erp/backup/prune_<실행시각>.json` 에 경로·크기·내용 통째 덤프.
  write_log·intake_log 는 90일 초과 행 수만 세어 로그에 남기고 삭제하지 않는다.
- cron: `/etc/cron.d/erp-prune` — 매일 03:30 KST `--apply` 실행, 로그 `/srv/erp/prune_versions.log`.
- 1회 실행 확인: dry-run·`--apply` 둘 다 완료, 삭제 0건(이미 기준 충족).

## 되돌리기

이번 실행은 삭제한 것이 없어 되돌릴 것도 없음. 향후 cron 이 실제로 지우는 날이 오면
`/srv/erp/backup/prune_<시각>.json` 의 각 항목 `content` 를 그 항목의 `path` 에 그대로 다시 쓰면
복원된다.

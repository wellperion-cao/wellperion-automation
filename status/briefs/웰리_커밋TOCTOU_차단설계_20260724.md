## ③ 앞선 사례 대조 — 왜 GUARDED로 닫혔는데 또 터졌나

`ssot/incidents.json` 전수(INC-001~029)를 확인했다. **시모 브리프가 "기억에 박제됐다"고 언급한 2건("임시 인덱스 커밋 → 옛 blob 잔류" / "임시 인덱스는 라이브 index cp 말고 read-tree HEAD로 시작")과 문자 그대로 일치하는 별도 INC-ID는 incidents.json에서 찾지 못했다** — 지어내지 않고 정직히 "확인 불가"로 남긴다. 이 2건은 메모리 파일에만 기록된 것으로 보이며, incidents.json에 정식 등재되지 않았을 가능성이 있다.

incidents.json에서 **본질이 가장 가까운(7/21 이전, GUARDED로 닫힌) 선례 2건**은 다음과 같다 — 둘 다 "공유 워크트리에서 무관한 스테일 상태가 내 커밋에 섞인다"는 같은 본질이다.

| ID | 날짜 | 요약 | 차단조치(범위) | 상태 |
|---|---|---|---|---|
| INC-017 | 2026-07-20 | pre-commit 훅의 `sync_queue_mirror.py`가 디스크를 무조건 직독해 무관한 커밋에 **다른 세션의 스테일 `_queue.json` 사본**을 실어 날랐다 | `sync_one()`에 `require_staged` 인자 추가 — **`sync_queue_mirror.py` 이 스크립트 하나만** 인덱스 기반 확인으로 전환 | GUARDED |
| INC-022 | 2026-07-20 | INC-017과 같은 본질이 하루 4회+ 재발 — bare `git commit`(pathspec 없음)이 add~commit 사이 다른 세션이 staged해둔 무관 파일을 통째로 쓸어담음 | **5개 지정 스크립트**(`git_lock.py`·`auto_log_adhoc_to_queue.py`·`commit_ig_reach.py`·`commit_engagement.py`·`weekly_page_hygiene.py`)의 bare commit을 pathspec 스코프(`git commit -m … -- <파일>`)로 전환 | GUARDED |

**왜 이 두 GUARDED 조치가 7/21 사고를 못 막았나 — 코드로 확인한 이유:**
INC-017·INC-022 둘 다 "이 스크립트만" 또는 "이 5개 스크립트만"으로 **범위를 좁혀 수리**했다. INC-022 본문이 스스로 이 한계를 명시한다 — *"pathspec 도입은... 사람이 터미널에서 치는 bare 커밋까지는 못 막는다."* 7/21 사고의 `b96cac0ea`(CTO 배9468, Claude 세션 `session_01DeysMM9YomN5abF2TyP7oc`)는 이 5개 지정 스크립트 목록에 없다 — **세션이 직접(또는 다른 도구가) 실행한 통상적 커밋**으로 추정되며(코드에서 이 특정 커밋의 실행 경로 자체를 재구성할 수는 없어 이 부분은 추정), 이는 INC-017·INC-022가 애초에 겨냥한 범위(특정 자동화 스크립트) 밖이다. 즉 **"같은 본질 2회 GUARDED"는 매번 사고가 난 그 스크립트 1~5개만 막았을 뿐, "공유 워크트리에서 도는 모든 커밋"이라는 근본 범위를 막은 적이 없었다** — safe_commit.py(2026-07-23)가 처음으로 "전 C-Level 공용" 범위를 표방한 시도다.

추가로 **INC-029(2026-07-23, 3,156파일 삭제)** 는 safe_commit.py와 같은 날 발생했고 상태가 **OPEN**(GUARDED 아님)이다 — 차단조치 항목이 스스로 "★자동 차단 코드는 미구현 — 현재는 절차 규정 단계라 상태 OPEN 유지"라고 적어뒀다. 다만 코드 확인 결과, INC-029가 지목한 정확한 결함("read-tree 실패를 `2>/dev/null`로 삼킴")은 **현재 `safe_commit.py`에는 없다** — `_git_out()`이 returncode≠0이면 무조건 `RuntimeError`를 던지고, 이는 함수 최상위 `except Exception`에서 잡혀 `committed=False`로 조용히 실패 처리되지 지금은 삼켜지지 않는다(라인 55-76, 272-273). 즉 INC-029의 구체적 재발 경로는 코드로 재차단됐지만, **"절차 규정만 있고 자동 차단 코드는 없다"는 INC-029의 상태(OPEN) 자체는 아직 "누구나 safe_commit.py를 실제로 쓰는가"를 강제하는 장치가 없다는 뜻과 같다** — 이것이 ④의 우회 경로 문제로 이어진다.

## ④ safe_commit 우회 경로 전수

**있다 — 최소 7개 파일 + 1개 공용 헬퍼(사실상 그 이상)**, 전부 pathspec 스코프 bare `git commit`으로, safe_commit.py의 HEAD 재검증+CAS를 거치지 않는다.

| 소스:라인 | 커밋 방식 |
|---|---|
| `scripts/auto_log_adhoc_to_queue.py:365` | `["git", "commit", "-m", msg, "--", QUEUE_REL]` |
| `scripts/commit_ig_reach.py:41` | `["git", "commit", "-m", "auto(cto): ...", "--"] + FILES` |
| `scripts/commit_engagement.py:45` | `["git", "commit", "-m", "auto(cmo): ...", "--"] + FILES` |
| `scripts/erp_status_publisher.py:418` | `["git", "commit", "-m", ...]` |
| `scripts/git_lock.py:207-208` (`git_commit_push()` 공용 헬퍼) | `["git", "commit", "-m", message, "--"] + paths` — **이 헬퍼 자체가 다른 스크립트들에서 재사용될 수 있는 구조**이며, 주석(라인 200-206)에 "GitLock은 이 함수를 호출하는 프로세스끼리만 직렬화하고, 사람이 터미널에서 치는 bare `git commit`이나 이 락을 안 쓰는 다른 스크립트의 동시 `git add`는 못 막는다"고 **스스로 명시**돼 있다. |
| `scripts/parking_revenue_crawler.py:191` | `["git", "commit", "-m", "chore(parking): ...", ...]` |
| `scripts/weekly_page_hygiene.py:362` | `["git", "commit", "-m", msg, "--", path]` |

이 7개는 전부 INC-022 수리로 pathspec은 있으나(다른 세션 staged 혼입은 막힘), **safe_commit.py의 read-tree HEAD+HEAD재검증+update-ref CAS는 적용돼 있지 않다** — 즉 이론상 7/21과 같은 순수 TOCTOU(내 add~commit 사이 다른 프로세스의 정상 커밋이 HEAD를 옮기는 경우)에는 여전히 노출돼 있다(pathspec은 "남의 staged 파일이 섞이는 것"은 막지만 "내가 스코프한 파일들의 베이스가 된 트리 자체가 낡았는지"는 검증하지 않는다).

**더하여, 반대 방향의 우회도 있다:** safe_commit.py는 `commit-tree`+`update-ref`를 쓰므로(라인 20-21 자체 주석 확인) **git의 `pre-commit`/`post-commit` 훅 메커니즘을 아예 발화시키지 않는다.** 특히 INC-029 직후 신설된 `scripts/precommit_phantom_delete_guard.py`("유령 삭제" 차단 — 삭제로 staged된 경로가 작업트리에 실존하면 커밋 자체를 **차단**, `.git/hooks/pre-commit` 최상단 ⓪ 우선순위로 확인)는 **`git commit` 경로에만 걸리고, `safe_commit.py` 경로에는 걸리지 않는다.** 이는 이번 조사에서 코드로 직접 확인한, 팀장이 요청한 "삭제 혼입을 막는 검사"의 정확한 현재 상태다 — **가장 강력한 삭제 전용 차단 가드가 정작 이번 사고와 가장 밀접한 safe_commit.py 경로에서는 작동하지 않는다.**

`git commit --no-verify`(모든 훅 우회)와 `env SKIP_PHANTOM_DELETE_GUARD=1` 같은 명시적 우회 스위치도 각 가드에 하나씩 존재하나, 이건 설계상 의도된 비상탈출구(문서에 명시)이지 은닉된 구멍은 아니다.

**결론: 우회 경로 있음 — 최소 7개 스크립트(+1 공용 헬퍼) + safe_commit.py 자체의 훅 미발화 특성.** 가드가 있어도 "안 쓰면 그만"인 구조다.

## ⑤ 차단안 비교 + 추천

목표: **"커밋 대상 경로 밖의 파일이 삭제로 들어가는 것"을 커밋이 origin에 닿기 전에 기계가 거부.**

| 안 | 위치 | 오탐 위험 | 우회 가능성 | 구현 난이도·담당 후보 |
|---|---|---|---|---|
| **A. safe_commit.py 내부에 phantom-delete 판정을 update-ref *이전*으로 선검증** — `write-tree` 직후 `head_tree`와 `tree`를 비교해 삭제로 바뀐 경로 중 작업트리에 실존하는 게 있으면 그 자리에서 커밋 자체를 포기(commit-tree/update-ref 미실행, 재시도 없이 즉시 실패 반환) | `safe_commit.py` 내부 1곳 | **낮음** — 이미 `precommit_phantom_delete_guard.py`에서 검증된 로직(디스크 존재 여부)을 그대로 재사용, 진짜 의도된 삭제(작업트리에서도 지운 경우)는 통과 | **맨손 `git commit-tree`+`update-ref`를 직접 치는 경우만 우회 가능(사실상 아무도 이렇게 안 함)**. safe_commit.py를 안 쓰고 그냥 `git commit`을 치는 경우엔 여전히 우회되지만, 그건 기존 pre-commit 훅(phantom-delete-guard)이 이미 커버 — 두 경로 합쳐 사각 최소화 | **낮음**(~20줄, 기존 로직 이식) · 시토 |
| **B. safe_commit.py가 커밋 직전 `git hook-run pre-commit`(또는 phantom-delete-guard.py를 직접 subprocess로) 호출해 기존 훅을 재사용** | `safe_commit.py` 내부, `commit-tree` 직전 | **낮음** — A와 동일 로직, 코드 중복 없이 기존 가드 그대로 재사용(향후 pre-commit 훅에 새 가드가 추가돼도 자동으로 같이 적용됨) | A와 동일 | **낮음~중간**(훅 스크립트를 GIT_INDEX_FILE=임시인덱스 상태로 안전하게 호출하려면 환경변수 전달 검증 필요) · 시토 |
| **C. 저장소 정책으로 커밋 경로를 safe_commit.py 하나로 강제 일원화** — pre-commit 훅이 `SAFE_COMMIT_TOKEN` 같은 마커 없는 커밋을 전부 거부 | 전역 pre-commit 훅 | **높음** — 시모 브리프가 이미 우려한 그대로, 6명 C-Level·전 자동화가 동시에 safe_commit.py로 갈아타야 하며 훅 설정 하나만 어긋나도 전원 커밋 불가 | `--no-verify`로는 여전히 우회 가능(git 자체 한계, 근본 봉인 불가) | **높음**(전 커밋 경로 전환+회귀 검증 필요) · 시토(구현)+웰리(오케스트레이션 승인) |

**추천: A안.** 이유 — ④에서 확인한 가장 시급한 결함(safe_commit의 혼입검사가 update-ref *이후*라 이미 만들어진 나쁜 커밋을 그대로 push해버림)을 정확히 겨냥하면서, 이미 실전 검증된 phantom-delete 로직을 재사용해 오탐 위험이 낮고, 수정 범위가 `safe_commit.py` 한 파일에 그쳐 6명 공용 경로 전체를 흔들 위험이 없다. B안은 A의 사상적 확장(기존 훅 재사용)이라 A 구현 후 리팩터 후속으로 붙여도 되고, C안은 "우회 경로 자체를 없앤다"는 더 근본적 목표지만 team-lead 표현대로 "잘못 조이면 6명 커밋이 전부 막히는" 고위험 변경이라 A·B로 먼저 안전망을 두텁게 한 뒤 별도 승인 절차를 거쳐 검토할 사안으로 본다. 담당 후보는 A·B 모두 시토(자동화·가드 소유), 최종 우선순위·시행 시점 판단은 웰리(오케스트레이션) 몫으로 남긴다.

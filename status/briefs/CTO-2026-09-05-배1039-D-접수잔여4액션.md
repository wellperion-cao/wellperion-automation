# 배1039-D — 종합접수처 잔여 쓰기 4액션 서버 원장 라우트 (2026-09-05 시토)

레인 D. 배1039 "다 서버 원천으로"의 종합접수처(reception) 몫 마지막 조각 — 1039-C 가 손 안 댄
`reg_delete`·`lf_handover`·`lf_delete`·`hold_complete` 4개를 서버 원장 직접 라우트로 옮겼다. GAS(RECEPTION_EXEC_URL)는
이제 이 4액션에서도 부르지 않는다. 화면(`종합접수처_현황.html`)·워드프레스는 손 안 댐 — 시우 소관.

## 새 주소 (server/erp_api/api_reception.py)

| 주소 | 대체 | 원장 | 응답 모양 |
|---|---|---|---|
| `POST /api/reception/delete` | `reg_delete` | `reception_items` 행 삭제 | `{ok,id,category,deleted:1,message}` (GAS 그대로) |
| `POST /api/reception/lost/handover` | `lf_handover` | `lost_found` 행 갱신(상태→수령완료) | `{ok,id,status,signPurgeAt}` |
| `POST /api/reception/lost/delete` | `lf_delete` | `lost_found` 행 삭제 | `{ok,id,deleted:1}` |
| `POST /api/reception/hold/complete` | `hold_complete` | `hold_items.done` 갱신 | `{ok,matched:true}` |

없는 ID → 404, 잘못된 값(핀 오류·필수칸 누락·이미 처리됨) → 400 — GAS 는 전부 200+ok:false 였으나
이번 4개는 상태코드를 실제 의미에 맞게 갈랐다(팀리드 지시).

## 세부

- **reg_delete → /delete**: 삭제 비밀번호(PIN) 서버 재검증 그대로(`REG_DELETE_PIN` env, 기본값 GAS 와 동일 `1200`).
  category 지정 시 그 카테고리 행만(라벨·키 둘 다 허용) — `_cat_resolve()`.
- **lf_handover → /lost/handover**: 서명(base64)은 `save_photo()` 로 서버 디스크에 저장(기존 사진 저장과 같은
  경로 · `lost-found` 서브디렉터리) — GAS 의 Drive 서명 폴더 대신. 파기예정일(수령+6개월)은 `_add_months()` 신설
  (stdlib 만, dateutil 안 씀). 이미 처리된 건(상태≠게시중) 재수령 거부(멱등) 그대로.
- **lf_delete → /lost/delete**: 그대로 단순 삭제.
- **hold_complete → /hold/complete**: GAS 원본은 시트 "휴회접수" 탭에 처리메모를 적었지만, 서버에는 그 시트의
  거울이 없다(휴회 원장은 `hold_items` = `member_hold_intake_list` 미러 + `hold_done_keys` 조인). 그래서 매칭 대상을
  `hold_items` 행 자체로 바꿨다 — 정규화(phone·start·name)는 `sync_reception.hold_key()` 를 그대로 재사용(새 계산
  안 만듦), 일치 행의 `done` 을 True 로 직접 적는다.
  - ★부수 변경: `sync_reception.replace_hold()` 를 "한 번 done=True 면 되돌리지 않는다(sticky)" 로 고쳤다.
    안 고치면 5분 뒤 동기화가 GAS `hold_done_keys`(휴회접수 시트는 여전히 그대로라 이 값을 모른다)로 done 을
    다시 False 로 덮어써 버린다 — 서버 완료 표시가 5분마다 사라지는 회귀였다. selftest 로 기존 케이스도
    그대로 통과 확인.

## 배포·실측

- 배포: `server/erp_api/api_reception.py`·`server/erp_api/sync_reception.py` 만 scp → `sudo systemctl restart erp-api`
  (1039-C 방식, `deploy_api.sh` 전체 배포 안 함). 재기동 후 `systemctl is-active erp-api` = active,
  내부 health 200 확인.
- 실측(격리 테스트 행, 마커 `TEST-1039D-*`/`[테스트]`, 서버에서 직접 python 으로 원장에 심고 로컬 HTTP 호출 후 삭제):

```
delete/bad-pin          -> 400 BAD_PIN
delete/no-id            -> 400 id 필수
delete/not-found        -> 404 해당 접수ID를 찾을 수 없습니다
delete/ok               -> 200 deleted:1
lost/handover/no-id            -> 400 습득ID 필수
lost/handover/missing-receiver -> 400 수령자 성함은 필수입니다
lost/handover/not-found        -> 404 해당 습득ID를 찾을 수 없습니다
lost/handover/ok               -> 200 status=수령완료, signPurgeAt=2027-03-05
lost/handover/already          -> 400 ALREADY_HANDLED(멱등 확인)
lost/delete/no-id       -> 400 id 필수
lost/delete/not-found   -> 404 해당 습득ID를 찾을 수 없습니다
lost/delete/ok          -> 200 deleted:1
hold/complete/no-id-info -> 400 식별정보 부족
hold/complete/not-found  -> 404 일치 행 없음
hold/complete/ok         -> 200 matched:true
```

DB 검증: 삭제 2건 모두 조회 시 None(실제 삭제 확인) · lf_handover 대상 행 status=수령완료로 갱신 확인 ·
hold_items 대상 행 done=True 확인. 테스트 행·업로드된 테스트 서명 파일 전부 삭제(격리 원복 완료).

## 시트 원본(157 이전)도 같은 라우트로 처리됨

배984 부터 시트는 동결(읽기 전용)이지만, 그 이전에 시트에서 넘어온 옛 접수건도 sync_reception.py 가
서버 원장(`reception_items`/`lost_found`/`hold_items`)에 이미 미러돼 있으므로, 이번 4라우트는 옛 건이든
새 건이든 구분 없이 같은 서버 원장을 보고 처리한다 — 예외 없음.

## 안 건드린 것

- `api_write.py` 의 `write_reception`/`_RECEPTION_WRITES`·`_gas_key` 분기 — 그대로 둔다. 화면이 이 4주소로
  넘어오기 전까지는 종전처럼 `/api/write`→GAS 경로가 살아 있어야 한다(다른 레인이 그 파일을 만질 수 있어
  이번엔 읽기만 했다).
- 화면(`종합접수처_현황.html`)·워드프레스 — 시우 전담.
- `reg_staff_suggest` — 범위 밖(쓰기 아님·GATED 조회일 뿐이라 이번 배 대상 아님).

# ERP·관리자 콘솔 벤치마킹 — 실제 제품의 레이아웃과 정보 밀도

작성 2026-09-10 · 조사 대상 = 우리 ERP 3층(회사 관리자 / 파트너사 관리자 / 파트너사 직원) 화면 설계 기준

## 0. 조사 방법 — 무엇을 근거로 썼나

수치는 셋 중 하나로만 적었다. 추정치는 없다.

| 근거 종류 | 뜻 | 해당 제품 |
|---|---|---|
| 배포 CSS 실측 | 실제 제품이 쓰는 CSS 파일을 내려받아 규칙을 직접 읽음 | SAP Fiori(Horizon), Salesforce Lightning |
| 라이브 화면 실측 | 브라우저로 실제 화면을 열고 DOM 크기를 잼 | Odoo 17 데모 백엔드, Atlassian 디자인 사이트 |
| 1차 문서 | 제조사 공식 문서의 명시 수치·구조 설명 | IBM Carbon, Microsoft Dynamics·M365, NHN Cloud, 채널톡, 토스페이먼츠 |

확인 못 한 것은 각 항목에 "확인 못 함"이라 적었다.

## 1. 제품별 관찰

### 1-1. SAP Fiori (Horizon 테마) — 대기업 ERP 표준
근거: 배포 CSS 실측 — `https://sdk.openui5.org/resources/sap/f/themes/sap_horizon/library.css`, `.../sap/tnt/...`, `.../sap/m/...`, `.../sap/ui/core/...`

| 요소 | 값 | CSS 근거 |
|---|---|---|
| 상단 셸바 높이 | 48px (3rem) | `.sapFShellBar{height:3rem}` |
| 좌측 메뉴 폭 | 240px (15rem) | `--sapTntSideNavigation_ExpandedWidth:15rem` |
| 본문 기본 글자 | 14px (.875rem) | `--sapFontSize:.875rem` |
| 작은 글자 | 12px (.75rem) | `--sapFontSmallSize:.75rem` |
| 표 행 높이 — 여유(cozy) | 44px (2.75rem) | `--sapElement_LineHeight:2.75rem` |
| 표 행 높이 — 조밀(compact) | 32px (2rem) | `.sapUiSizeCompact .sapMListTblRow{height:2rem}` |
| 표 머리행 높이 | 40px (2.5rem) | `.sapMListTblHeader{height:2.5rem}` |

핵심: Fiori 는 밀도를 **두 모드로 고정**해서 판다. 마우스를 쓰는 데스크톱 업무 화면은 compact(32px 행), 터치는 cozy(44px 행). 같은 컴포넌트에 클래스 하나(`sapUiSizeCompact`)를 붙여 전환한다.
첫 화면(런치패드)은 앱 타일 격자다. 셸바는 뒤로가기·브랜딩·페이지 제목·검색·알림·사용자 메뉴만 담는다 — 업무 기능은 셸바에 올리지 않는다. (문서: https://www.sap.com/design-system/fiori-design-web/v1-145/foundations/integration-and-services/sap-fiori-launchpad/launchpad — 본문 접근은 403 으로 막혀 요약만 검색 결과로 확인, 수치는 위 CSS 실측이 근거)

### 1-2. Salesforce Lightning (SLDS) — SaaS 콘솔 표준
근거: 배포 CSS 실측 — `https://cdnjs.cloudflare.com/ajax/libs/design-system/2.17.5/styles/salesforce-lightning-design-system.min.css`

| 요소 | 값 | CSS 근거 |
|---|---|---|
| 전역 헤더 높이 | 50px (3.125rem) | `.slds-global-header{height:3.125rem;padding:.5rem 0}` |
| 앱 네비게이션 바 높이 | 40px (2.5rem) | `.slds-context-bar{height:2.5rem;border-bottom:3px solid #1b96ff}` |
| 본문 기본 글자 | 13px (.8125rem) | `.slds-text-body_regular{font-size:.8125rem}` |
| 작은 글자 | 12px (.75rem) | `.slds-text-body_small{font-size:.75rem}` |
| 표 셀 여백 | 상하 4px / 좌우 8px | `.slds-table td,.slds-table th{padding:.25rem .5rem;white-space:nowrap}` |
| 표 머리행 | 배경 #f3f3f3, 굵기 700 | `.slds-table thead th{background-color:#f3f3f3;font-weight:700}` |
| 전역 검색창 폭 | 기본 536px, 최소 440px | `flex:0 1 33.5rem;min-width:27.5rem` |

핵심 셋. ① **본문이 13px** 이다 — 문서가 아니라 도구이기 때문이다. ② 표 셀은 `white-space:nowrap` 으로 줄바꿈을 막아 한 행을 한 줄로 고정한다(행 높이가 들쭉날쭉해지지 않는다). ③ 헤더가 **2단**이다 — 위 50px 는 회사/계정 차원(검색·알림·사용자), 아래 40px 는 지금 보는 앱의 탭. 이 2단 분리가 "지금 어느 앱의 어느 화면인가"를 항상 보이게 한다.

### 1-3. IBM Carbon — 명시 수치가 가장 촘촘한 공개 디자인 시스템
근거: 1차 문서 소스 — `https://raw.githubusercontent.com/carbon-design-system/carbon-website/main/src/pages/components/UI-shell-header/style.mdx`, `.../UI-shell-left-panel/style.mdx`, `.../data-table/style.mdx`

| 요소 | 값 |
|---|---|
| 상단 헤더 높이 | 48px |
| 헤더 안 아이콘 버튼 | 48×48px |
| 제품명 글자 | 14px / 600 |
| 좌측 패널 폭 | 256px |
| 좌측 메뉴 링크 높이 | 32px |
| 선택 표시 좌측 띠 | 4px |
| 표 행 높이 5단 | xs 24 / sm 32 / md 40 / lg 48 / xl 64px |
| 표 머리 글자 | 14px / 600 (SemiBold) |
| 표 본문 글자 | 14px / 400 |
| 열 사이 여백 | 16px |
| 툴바 높이 | 큰 48px / 작은 32px (행 높이와 짝) |

핵심: 행 높이를 **다섯 단계로 이름 붙여 파는 것**. 그리고 툴바·일괄작업 바의 높이를 행 높이와 짝지어 고정한다(48px 툴바는 lg/xl 행과, 32px 툴바는 xs/sm 행과). 밀도를 화면마다 눈대중으로 정하지 않는다.

### 1-4. Odoo 17 — 중소기업 ERP, 좌측 메뉴가 없는 쪽
근거: 라이브 실측(브라우저로 `https://demo3.odoo.com/odoo/contacts` 를 열고 DOM 측정) + 소스 SCSS `https://raw.githubusercontent.com/odoo/odoo/17.0/addons/web/static/src/scss/primary_variables.scss`, `.../webclient/navbar/navbar.variables.scss`

| 요소 | 실측값 |
|---|---|
| 상단 네비바 높이 | 46px (`$o-navbar-height: 46px`) |
| 컨트롤 패널(제목+검색+버튼) 높이 | 58px, 여백 8px / 좌우 16px / 아래 16px |
| 목록 행 높이 | 42px (실측, 3행 연속 동일) |
| 본문 기본 글자 | 14px (`$o-font-size-base: 14px`) |
| 표 안 작은 글자 | 13px / 12px 단계 존재 |
| 빵부스러기(breadcrumb) 높이 | 30px (`$o-cp-breadcrumb-height`) |

핵심: Odoo 는 **좌측 메뉴를 아예 안 쓴다.** 상단 네비바에 앱 전환 + 그 앱의 메뉴를 얹고, 가로 폭 전부를 목록에 준다(실측 목록 표 폭 = 브라우저 폭 그대로 1264px). 화면 위에서 아래로 46px 네비바 → 58px 컨트롤 패널 → 나머지 전부 표. 헤더 영역 합계가 104px 뿐이다.

### 1-5. Microsoft Dynamics 365 / 모델 기반 앱 — 좌측 사이트맵의 교과서
근거: 1차 문서 — https://learn.microsoft.com/en-us/power-apps/user/navigation

- 좌측 내비게이터(사이트맵) 구성: **앱 → 작업영역(area) → 테이블**의 3단. 우리 3층 구조와 층수가 같다.
- 좌측 메뉴 상단 고정 항목: **Recent(최근)** — 최근 연 행 최대 10개, **Pinned(고정)** — 즐겨찾기 최대 25개(한 테이블당 최대 15개).
- 좌측 메뉴는 **접기/펴기 버튼**으로 본문 폭을 넓힌다. 그룹은 접을 수 있게 만들 수 있다.
- 작업영역 전환기(area switcher)는 **좌측 하단**에 있고, 작업영역이 2개 이상일 때만 나타난다.
- 목록 화면 기본 구성: 체크박스 열 → 열 머리 클릭 정렬/필터 → 고급 필터 패널 → 명령 바(선택 후 일괄 작업, Excel 내보내기) → 검색 → 알파벳 점프 바 + 페이지 넘김.
- 폭 좁을 때는 앱 이름이 사라지고 사이트맵 버튼 안으로 들어간다.

### 1-6. Microsoft 365 관리 센터 다중 테넌트 — 우리 1층과 같은 화면
근거: 1차 문서 — https://learn.microsoft.com/en-us/microsoft-365/admin/multi-tenant/manage

- **테넌트 전환기(Tenant switcher)**: 상단에서 현재 테넌트 이름을 눌러 목록을 열고, 검색으로 골라 이동한다.
- **All tenants(모든 테넌트) 페이지** = 1층의 첫 화면. 한 줄에 테넌트 하나씩, 그 줄에 **서비스 상태 / 열린 지원 요청 수 / 제품·청구 / 사용자 수**가 함께 붙는다.
- 자주 가는 테넌트는 **맨 위로 고정(pin)** 할 수 있고, 즐겨찾기로 표시하면 그 줄이 자동으로 펼쳐져 상태 상세를 바로 보여준다.
- 전사 서비스 상태 화면은 **집계 먼저**다: 전체 장애 건수, 권고 건수, 장애가 있는 서비스 수 → 그 다음 유형·서비스별 필터 → 개별 장애를 누르면 "영향받은 테넌트" 탭에 목록이 나오고 **CSV 내보내기**가 붙는다.
- 개별 테넌트로 들어가면 그 테넌트의 일반 관리 센터가 그대로 열린다 — 즉 1층은 **2층 화면을 다시 만들지 않고, 2층으로 들어가는 문**이다.

### 1-7. NHN Cloud 콘솔 — 조직/프로젝트 2계층 권한 모델
근거: 1차 문서 — https://docs.nhncloud.com/ko/nhncloud/ko/console-user-guide/

- 계층: **조직(Organization) → 프로젝트(Project) → 멤버**.
- 역할이 층별로 따로 있다. 조직 레벨 = OWNER / ADMIN / ORG_MEMBER_ADMIN, 프로젝트 레벨 = ADMIN / PROJECT MEMBER ADMIN.
- 멤버에게는 역할과 역할 그룹을 부여할 수 있다.
- 화면 구성(상단바 항목, 좌측 메뉴 수치, 대시보드 내용)은 이 문서에 없다 — **확인 못 함**.

### 1-8. 채널톡 데스크(관리자) — 메뉴가 길어졌을 때의 한국식 해법
근거: 1차 문서 — https://docs.channel.io/help/ko/articles/새로워진-채널톡-관리자-화면-채널-웍스-소개-1c2c8d3e

- 한 줄로 길게 늘어서 있던 좌측 메뉴를 업무 성격에 따라 **[고객] · [팀] · [AI CoS] 세 묶음**으로 나누고, **상단 탭으로 묶음을 전환**한다. 탭을 고르면 그 업무에 필요한 메뉴만 남는다.
- 시스템 로그는 기본 접힘(`접힌 로그 (4)`)으로 감춘다.
- 우측 상세 패널은 아이콘을 빼고 라벨-내용을 좌우 한 쌍으로 붙여 압축했다.
- 색은 위계 경쟁을 줄이는 쪽으로 바꿨다(내부 대화 노랑/주황 → 차분한 연보라).

### 1-9. 토스페이먼츠 상점관리자
근거: 1차 문서 — https://docs.tosspayments.com/resources/glossary/dashboard , https://www.tosspayments.com/blog/articles/29797

- 메뉴 축 = 결제 / 정산 / 결제 조회 / 이용정보. 업무 동사 단위지 데이터 모델 단위가 아니다.
- 조회 화면은 **일자·상점(MID)·결제수단 필터 + 목록 + 엑셀 내려받기**가 한 세트. 조회 기간·다운로드 건수 제한 없음을 기능으로 내세운다.
- 상점아이디(MID)별로 계약 상태·정산·수수료를 갈라 본다 — 사실상 테넌트 전환과 같은 축.
- 화면 수치(메뉴 폭·행 높이)는 로그인이 필요해 **확인 못 함**.

### 1-10. Atlassian 디자인 시스템
근거: 검색 결과 https://atlassian.design/components/navigation-system/layout , https://atlassian.design/foundations/spacing + 라이브 실측(atlassian.design 본문 글자 = 14px)

- 좌측 사이드바 240px + 본문 유동 폭.
- 간격 토큰의 기본 단위 = **8px**, 모든 간격 토큰이 8의 배수(space.200 = 16px).
- 문서 사이트 본문 글자 실측 14px.

## 2. 수치 한 장 요약 — 실측·1차 문서만

## 2-1. 항목이 100장을 넘을 때 — 실제 제품은 카드 격자를 쓰지 않는다

우리 2층은 실행 모듈 카드가 100장을 넘고 그룹이 5개(자주 여는 것·회원·운영·점검·경영)다. 같은 문제를 이미 겪은 제품들이 무엇을 골랐는지 본다.

| 제품 | 항목 수 | 고른 해법 | 근거 |
|---|---|---|---|
| AWS 관리 콘솔 | 서비스 200개 이상 | **통합 검색(Unified Search) + 즐겨찾기(Favorites) + 최근 방문(Recently visited)**. 첫 화면(Console Home)은 위젯이며 사용자가 추가·삭제·재배치한다 | https://docs.aws.amazon.com/awsconsolehelpdocs/latest/gsg/what-is.html (라이브 본문 확인) |
| Salesforce | 앱 + 객체 수백 | **앱 런처의 "Find an app or item" 검색 상자 — 타이핑하는 대로 결과**. 앱은 타일(All Apps), 객체·항목은 **목록**(All Items)으로 분리. 사용자가 타일을 끌어 개인 정렬하면 관리자 정렬을 덮어씀 | https://help.salesforce.com/s/articleView?id=sf.lex_find_your_stuff.htm |
| Dynamics 365 | 앱→작업영역→테이블 | **좌측 트리 + 최근 10건 + 고정 25건**, 그룹은 접힘 가능, 작업영역 전환기는 좌측 하단 | https://learn.microsoft.com/en-us/power-apps/user/navigation |
| SAP Fiori 런치패드 | 앱 수백 | 첫 화면은 **타일**이지만 그 타일은 "자주 쓰는 것만 올려둔 개인 페이지"이고, 전부 찾기는 셸바 검색으로 한다 | https://www.sap.com/design-system/fiori-design-web/v1-145/foundations/integration-and-services/sap-fiori-launchpad/launchpad (요약 확인, 본문 403) |
| 채널톡 데스크 | 메뉴 20개대 | 좌측 메뉴를 3묶음으로 나누고 **상단 탭으로 묶음 전환** — 탭을 고르면 그 업무 메뉴만 남음 | https://docs.channel.io/help/ko/articles/새로워진-채널톡-관리자-화면-채널-웍스-소개-1c2c8d3e |
| Odoo | 앱 수십 | 상단 앱 메뉴 하나에 모아두고, 목록 화면은 표 | 라이브 실측 |

읽어낼 규칙 넷:

1. **100장이 넘으면 첫 화면은 "전부"가 아니라 "내 것"이다.** AWS·Fiori·Dynamics 모두 첫 화면에 전체 목록을 깔지 않는다. 최근 쓴 것과 즐겨찾기만 올린다. 전체는 검색이나 별도 목록으로 간다.
2. **검색이 1순위 도구다.** 항목이 100장을 넘으면 스크롤로 찾는 사람은 없다. AWS는 검색을, Salesforce는 타이핑 즉시 필터되는 상자를 상단 고정으로 둔다.
3. **"앱"은 타일, "항목"은 목록.** Salesforce가 둘을 명시적으로 갈랐다(All Apps = 타일, All Items = 리스트). 100장짜리는 항목이지 앱이 아니다 — 목록이 맞다.
4. **개인화가 정렬을 이긴다.** Salesforce는 사용자의 드래그 정렬이 관리자 정렬을 덮어쓴다. AWS는 위젯을 사용자가 재배치한다. "자주 여는 것" 그룹은 사람마다 다르다.

즉 카드 100장을 세로로 잇는 대신: **좌측 트리(그룹 5개 · 접힘) + 상단 검색 + 첫 화면은 최근·즐겨찾기 + 전체는 표.**

## 2-2. 색·모서리·구분선 — 실제 콘솔이 쓰는 값

근거: SLDS 배포 CSS 실측, Fiori Horizon 배포 CSS 실측, Odoo 17 소스 SCSS.

| 항목 | Salesforce(SLDS) | SAP Fiori(Horizon) | Odoo 17 |
|---|---|---|---|
| 화면 바탕 | `#f3f3f3`(shade) | `--sapBackgroundColor:#f5f6f7` | 흰색 |
| 콘텐츠 면 | `#fff`(theme_default) | `--sapList_Background:#fff` | `$o-view-background-color: white` |
| 셸/상단 바탕 | `#fff` | `--sapShell_Background:#eff1f2` | 흰색 |
| 구분선·테두리 | `1px solid #e5e5e5` | `--sapList_BorderColor:#e5e5e5` / 그룹 `#d9d9d9` | `$o-border-color: #dee2e6` |
| 모서리 반경 | `.25rem = 4px` (`.slds-box`) | `.75rem = 12px` | Bootstrap 기본(작음) |
| 본문 글자색 | `#181818` | `--sapTextColor:#131e29` | `$o-main-text-color: #495057` |
| 보조 라벨색 | — | `--sapContent_LabelColor:#556b82` | `$o-gray-600 #6c757d` |
| 얼룩 무늬(zebra) | 짝수 행 `#f3f3f3` | 확인 못 함 | 확인 못 함 |

읽어낼 규칙 셋:

1. **바탕은 무채색 회색(#f3f3f3~#f5f6f7)이나 흰색이다.** 세 제품 모두 채도 있는 바탕색을 안 쓴다. 베이지(#F4F0EB)는 채도가 있는 종이 톤이라 "문서"로 읽힌다.
2. **면을 나누는 것은 그림자가 아니라 1px 선이다.** 세 제품의 구분선이 전부 `#e5e5e5`~`#dee2e6` 한 값이다. 카드를 띄우는 그림자 대신 선 하나로 가른다.
3. **모서리는 작다.** SLDS 4px, Odoo Bootstrap 기본. Fiori 만 12px 로 둥근데 그건 타일 전용 톤이다. 표·패널에 12px 이상 둥근 모서리를 주면 데이터 화면이 카드 화면으로 읽힌다.

## 3. 운영사 콘솔 vs 고객사 콘솔 — 무엇이 다른가

근거: https://learn.microsoft.com/en-us/microsoft-365/admin/multi-tenant/manage , https://docs.nhncloud.com/ko/nhncloud/ko/console-user-guide/ , https://kanopylabs.com/blog/how-to-build-a-multi-tenant-admin-dashboard (2차)

| 구분 | 운영사(플랫폼) 콘솔 | 고객사(테넌트) 콘솔 |
|---|---|---|
| 첫 화면 | 고객사 **목록** — 한 줄에 한 고객사, 상태·미해결 건수·청구·사용자 수 | 자기 회사의 오늘 상태·자기 모듈 |
| 축 | 가로(고객사 간 비교·집계) | 세로(자기 데이터 깊이) |
| 이동 | 테넌트 전환기 + 즐겨찾기 고정 | 전환기 없음(자기 회사 하나) |
| 고유 기능 | 임퍼소네이션, 전사 집계, 기능 플래그, 요금·정산 | 자기 사용자·권한, 자기 청구서, 자기 감사 로그 |
| 화면 재사용 | 개별 고객사로 들어가면 **2층 화면을 그대로 연다** | — |

관행 셋:
1. **전환기는 상단 좌측(제품명 옆)이나 좌측 메뉴 하단**에 둔다. Dynamics 의 작업영역 전환기는 좌측 하단, M365 테넌트 전환기는 상단이다. 어느 쪽이든 **한 자리에 고정**하고 검색을 붙인다.
2. **임퍼소네이션(대행 보기)은 운영사 전용**이며, 감사 로그가 반드시 따라붙는다(2차 자료 https://medium.com/@codebyzarana/building-a-secure-user-impersonation-feature-for-multi-tenant-enterprise-applications-21e79476240c). 대행 중에는 화면에 상시 배너로 "지금 누구로 보고 있는지"를 표시하는 것이 통상 관행이지만, 배너의 구체 규격은 **1차 자료로 확인 못 함**.
3. **권한은 층마다 따로 정의한다.** NHN Cloud 는 조직 역할과 프로젝트 역할을 이름부터 분리했다. 한 개의 역할 목록으로 3층을 다 덮지 않는다.

## 4. 안티패턴 — 관리 콘솔에서 하지 말아야 할 것

근거: NN/g https://www.nngroup.com/articles/complex-application-design/ , https://www.nngroup.com/articles/data-tables/ + 위 제품 관찰

1. **본문 글자 16px 이상.** 조사한 다섯 제품 전부 13~14px 다. 16px 는 읽을거리(문서·랜딩)의 크기다.
2. **본문 폭을 max-width 로 묶기.** Odoo 는 목록에 브라우저 폭 전부(실측 1264px)를 준다. 콘솔에서 가운데 정렬된 좁은 기둥은 열을 잘라먹는다.
3. **카드로 목록을 만들기.** 항목이 5개를 넘고, 항목마다 같은 속성(상태·날짜·수치)이 있고, 비교·정렬·검색이 필요하면 그건 표다. 카드는 항목 수가 고정이고 각각을 "들어가는 문"으로 쓸 때만 쓴다(Fiori 런치패드 타일이 그 경우다).
4. **설명문을 화면에 상주시키기.** 콘솔은 매일 오는 사람이 쓴다. 두 번째 방문부터 설명문은 잡음이다. 채널톡은 로그를 기본 접힘으로 감췄다.
5. **행마다 높이가 달라지는 표.** SLDS 는 `white-space:nowrap` 으로 한 행을 한 줄에 고정한다. 줄바꿈을 허용하려면 그 표만 별도 밀도로 선언한다.
6. **첫 열이 내부 ID.** NN/g: 기본 첫 열은 사람이 읽는 식별자여야 한다 — 자동 생성 ID 는 스캔이 안 된다.
7. **머리행이 스크롤에 사라짐.** NN/g: 화면보다 큰 표는 머리행·머리열을 고정한다.
8. **필터가 어디 있는지 모름.** NN/g: 필터는 발견 가능하고 빨라야 하며, 걸려 있을 때 그 사실이 눈에 보여야 한다.
9. **일괄 작업이 없음.** 체크박스 선택 + 전체 선택 + 표 위/아래의 작업 버튼이 표준 구성이다(NN/g, Dynamics 명령 바 동일).
10. **상단바에 업무 기능 얹기.** Fiori 셸바는 검색·알림·사용자·제목만 담는다. 업무 동작은 화면 안 컨트롤 패널로 내린다.
11. **접힘 아래 첫 화면에 경쟁 요소를 잔뜩.** NN/g 8원칙 중 "중요한 정보를 시각적으로 두드러지게" — 강조가 여러 개면 강조가 없다.
12. **밀도를 화면마다 눈대중.** Carbon 은 다섯 단계에 이름을 붙였고 Fiori 는 두 모드로 고정했다. 화면 작성자가 매번 px 를 고르게 두면 한 제품으로 안 읽힌다(우리가 이미 겪은 문제 — `assets/wp-ui.css` 머리말 기록: 한 화면에 글자 크기 9~48종, 배경색 49종).

## 5. 우리 3층에 그대로 적용할 설계 규칙

지금 상태(실측·팀 리드 보고 합침):

| 층 | 현재 | 문제 |
|---|---|---|
| 1층 | 오늘 좌측 메뉴 5영역으로 전환(현황·파트너사·환경 3벌·다운로드·구조 문서) | 방향은 맞음 — 폭·밀도 수치만 맞추면 됨 |
| 2층 | 상단 탭 3~4개 + 본문 모듈 카드 격자, 카드 100장 초과, 그룹 5개 | 카드가 세로로 끝없이 이어짐 — 100장은 목록이지 카드가 아님 |
| 공통 | 베이지 바탕 #F4F0EB + 흰 카드, 본문 15.5px, 상단바 58px, `erp/index.html` 은 `max-width:1100px`·`padding:40px 40px 80px`·카드 `minmax(280px,1fr)` | 조사한 다섯 제품 어디와도 안 맞음(바탕 채도·글자 1.5~2.5px 큼·상단바 8~12px 높음·본문 폭 제한) |

토큰 파일 `assets/wp-ui.css` 의 글자 6단계(11/12.5/14/17/22/26px)는 그대로 쓸 수 있다. 바꿀 것은 레이아웃·밀도·색이다.

1. **좌측 고정 메뉴 240px, 접으면 48px 아이콘 레일.** 3층 전부 같은 폭. (Fiori 240 · Atlassian 240 · Carbon 256)
2. **상단바 58px → 48px 한 줄.** 담는 것은 넷뿐 — 제품명, 현재 위치(빵부스러기), 전역 검색, 우측 끝 알림·사용자. 업무 버튼은 올리지 않는다. (Fiori 48 · Carbon 48 · Odoo 46)
3. **본문 15.5px → 14px, 표 안 13px, 라벨·단위 11px.** 16px 이상은 화면 표제에만. (SLDS 13 · Fiori/Carbon/Odoo/Atlassian 14)
4. **본문 `max-width` 를 지운다.** 좌측 메뉴 오른쪽 전부를 쓴다. 좌우 여백 16px·위 12px. 현재의 `max-width:1100px`·`padding:40px 40px 80px` 을 삭제한다. (Odoo 목록 실측 = 브라우저 폭 그대로)
5. **간격은 4의 배수만: 4·8·12·16·24·32.** 10·14·18·40·80 을 새로 박지 않는다. (Carbon 4px 배수 · Atlassian 8px 배수)
6. **표 행 높이 두 단으로 고정 — 조밀 32px(기본·마우스) / 여유 44px(터치).** 토큰 `--row-h` 하나로만 바꾸고 화면마다 정하지 않는다. (Fiori compact 32 / cozy 44 · Odoo 실측 42)
7. **표 머리행 40px, 배경 `#f3f3f3`, 글자 13px/600, `position:sticky; top:0`.** (SLDS 머리행 #f3f3f3·700 · Fiori 머리행 40px · NN/g 머리행 고정)
8. **표 셀은 `white-space:nowrap` 기본.** 긴 값은 말줄임 + 마우스 올리면 전체. 줄바꿈이 필요한 열만 예외 지정. (SLDS)
9. **첫 열은 사람이 읽는 이름.** 파트너사명·문서 제목·직원 이름. 내부 id 를 첫 열에 두지 않는다. (NN/g)
10. **모든 목록에 같은 4종 세트: 상단 필터 줄 / 열 머리 클릭 정렬 / 체크박스 + 일괄 작업 / 엑셀 내려받기.** 걸린 필터는 칩으로 보이게. (Dynamics 명령 바 · 토스 상점관리자 · NN/g)
11. **2층 모듈 100장을 카드 격자에서 걷어낸다.** 대신 셋: ① 좌측 트리에 기존 그룹 5개를 그대로 넣고 접히게 한다(항목 높이 32px·글자 13px) ② 상단바 검색이 모듈 이름을 타이핑 즉시 필터한다 ③ 본문 첫 화면은 **최근 연 것 10개 + 즐겨찾기**만 보여준다. (AWS = 검색+즐겨찾기+최근 · Salesforce = 타이핑 즉시 필터 · Dynamics = 최근 10/고정 25)
12. **"전체 모듈"은 카드가 아니라 표 한 장으로 본다.** 열 = 모듈명 / 그룹 / 최근 사용 / 담당 / 상태. 100줄짜리 표는 32px 행이면 한 화면에 20줄 이상 들어온다 — 카드로는 6장이다. (Salesforce: 앱은 타일, 항목은 All Items 목록)
13. **즐겨찾기는 사용자별로 저장하고 관리자 정렬을 덮어쓴다.** "자주 여는 것" 그룹을 사람이 직접 별표로 만든다. (Salesforce 개인 드래그 정렬 우선 · AWS Favorites)
14. **바탕색 #F4F0EB(베이지) → 무채색.** 화면 바탕 `#f3f3f3`, 콘텐츠 면 `#fff`, 상단바 `#fff`. 채도 있는 바탕을 쓰지 않는다. (SLDS #f3f3f3 · Fiori #f5f6f7 · Odoo 흰색)
15. **카드 그림자를 1px 구분선으로 바꾼다. 선 색 `#e5e5e5`, 모서리 반경 4px.** 흰 카드가 떠 있는 톤을 없앤다. (SLDS `.slds-box{border-radius:.25rem;border:1px solid #e5e5e5}` · Odoo `#dee2e6`)
16. **글자색을 두 단으로 고정: 본문 `#181818`, 보조 라벨 `#556b82` 급 회색.** 색은 상태(빨강=경보·초록=완료)에만 쓰고 장식으로 쓰지 않는다. (SLDS · Fiori LabelColor)
17. **1층 첫 화면 = 파트너사 표 한 장.** 열 = 파트너사명 / 상태 / 활성 모듈 수 / 이번 달 비용 / 마지막 접속 / 미해결 건수. 표 위에 집계 숫자 4개를 한 줄로. 파트너사명을 누르면 **그 회사의 2층 화면이 그대로 열린다**(2층을 다시 만들지 않는다). 대행 보기 중에는 상단 32px 띠로 "○○ 파트너사로 보는 중 · 나가기" + 로그. (M365 All tenants)
18. **권한 이름을 층마다 분리하고, 상주 설명문을 없앤다.** 1층 플랫폼관리자 / 2층 회사관리자 / 3층 사용자. 안내는 접힌 도움말 한 줄이나 물음표 아이콘으로 내린다. (NHN Cloud 조직/프로젝트 역할 분리 · 채널톡 로그 기본 접힘)

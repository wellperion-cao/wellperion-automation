## 3. `pages.yml`의 `on: push` 트리거 설정 — 필터 있음 (확인 완료)

```yaml
on:
  push:
    branches: [master]
    paths:
      - '3. 웰페리온 가이드/**'
      - '1. AI자료_아카이브/08_로고&워터마크/_assets/**'
      - 'ssot/**'
      - '.github/workflows/pages.yml'
```

필터는 있고 범위도 합리적이다(루트 최상위 `status/**`, `logs/**`, `telegram_bot/**` 등은 이미 배포 밖). **누락된 것은 이 범위 안에서의 예외(negation) 패턴 하나뿐** — `3. 웰페리온 가이드/status/_queue.json`을 빼는 줄이 없다.

## 5. 권고안 (시토 실행용)

### 권고 1 (최우선) — `_queue.json`을 배포 트리거에서만 제외

`pages.yml`의 `paths:` 목록에 negation 패턴 한 줄 추가(GitHub Actions는 같은 `paths:` 리스트 안에서 `!`로 예외 지정 가능, 순서상 포함 패턴 뒤에 와야 함):

```yaml
paths:
  - '3. 웰페리온 가이드/**'
  - '!3. 웰페리온 가이드/status/_queue.json'
  - '1. AI자료_아카이브/08_로고&워터마크/_assets/**'
  - 'ssot/**'
  - '.github/workflows/pages.yml'
```

**예상 효과:** 같은 6시간 샘플 기준 배포 트리거 88건→41건(53% 감소, §2의 47건 제거). 남는 41건 중 22건만 실제 화면 변경, 19건은 원래도 안 걸림 — 즉 트리거되는 배포의 실질 유효율이 25%→54%로 오른다.

**트레이드오프(결정 필요):** `_queue.json`을 트리거에서 빼면, 이 파일만 바뀐 순간에는 배포가 안 돌아서 GM1 항로 보드의 라이브 큐 상태가 "다음 진짜 배포 때까지" 갱신 안 된다. 위 권고대로면 진짜 배포는 평균 16분(6시간/22건)에 한 번꼴 — 지금보다 훨씬 자주 도는데도 그렇다(지금은 적체 때문에 사실상 몇 시간씩 안 도는 중이니 오히려 개선). 완전한 실시간성이 필요하면 대안으로 `_queue.json`을 Pages 빌드에 안 태우고 `raw.githubusercontent.com` 또는 jsDelivr(`cdn.jsdelivr.net/gh/...`) 경로로 직접 fetch하도록 프론트 URL만 바꾸는 방법이 있다 — 이건 git push 즉시 반영되고 Pages 재배포를 아예 안 기다린다. 이 파일 변경 후속판단은 시토 소관.

### 권고 2 (긴급, 별도 확인 필요) — concurrency 수정이 실효 없음

`cancel-in-progress:false`는 **"진행 중(in-progress)" 배포를 취소로부터 보호**할 뿐이다. GitHub Actions concurrency 그룹은 그룹당 **"진행 중 1개 + 대기 중 1개"만 유지**하는 구조로 보인다 — 새 푸시가 오면 `cancel-in-progress` 설정과 무관하게 **아직 시작 안 한 "대기 중" 러너를 곧바로 새 것으로 교체(취소)**한다. 실측: 수정 이후 취소된 실행 하나(`29712108218`)를 GitHub API로 조회하니 `jobs.total_count: 0` — **잡이 단 하나도 시작되기 전에 취소됐다.** 이건 워크플로 내부 취소가 아니라 큐 진입 단계에서 밀려난 것.

푸시 평균 간격(전체 136초)이 배포 1회 소요 시간(성공 4건 평균 76초) + 대기 시간(취소된 20건 평균 대기 181초)보다 촘촘해서, 대부분의 "대기 중" 배포가 자기 차례 오기 전에 다음 푸시로 교체당한다. **권고 1로 푸시 빈도를 줄이면 이 증상은 상당 부분 같이 풀릴 가능성이 높다**(남는 진짜 배포 간격이 16분이면 76초짜리 작업이 밀릴 이유가 없다) — 그래도 향후 다시 커밋이 몰릴 때를 대비해 concurrency 동작 자체를 시토가 한 번 더 확인해두길 권한다.

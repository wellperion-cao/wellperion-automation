## 2. 무엇이 AWS 로 가고 무엇이 PC 에 남나

**AWS 로 가는 것 (두뇌·상태·페이지)**

| # | 조각 | 어떻게 | 재사용하는 것 |
|---|---|---|---|
| ① | 두뇌 | 서버 API `POST /api/agent/{tenant}/draft` — 입력: 새로 들어온 대화 줄 + 마지막 처리 시각 / 출력: 초안·아침 질문 여부·보내면 안 되는 이유(가드) | `api_chat.py` 의 Bedrock 클라이언트 · 테넌트 프로필 · 미답 목록(`unanswered`) 그대로 |
| ② | 상태 | PostgreSQL 표 `agent_state(tenant_id, room, last_handled, day, sent_today)` | 장기결정 #2·#3 (`common/db.py` 하나 · tenant_id 칸) |
| ③ | 브리프·페르소나 | `/srv/erp/faq/{tenant}/profile.json` 에 `agent` 칸 추가 | 관리자 API 가 안 건드리는 칸(배포 때 갱신) |
| ④ | Before&After 페이지 | 이미 서버에 있다 — 변경 없음 | `deploy_dietcamp.sh` |

**PC 에 남는 것 (손)**

06:50 예약작업은 4단계 얇은 손으로 줄어든다: ① 카톡 내보내기 → ② 서버에 POST → ③ 받은 초안을 카톡으로 발신 → ④ GM 텔레그램 한 줄. `diet_camp_agent.py` 의 두뇌 코드(프롬프트·가드·상한 판단)는 서버로 옮기고 PC 에는 0 줄 남긴다. 서버가 지시하고 PC 가 손 노릇하는 구조다.

**왜 이 경계인가.** 카카오톡 PC 앱은 윈도우 화면 자동화라 서버로 옮길 수 없다(장기결정 문서 "바꾸지 않는 것"). 손까지 서버로 보내려면 카카오톡 채널(비즈니스) API 로 채널 자체를 바꿔야 한다 — 비용·심사가 붙는 💰 GM 결재 건이라 다캠 뒤 2·3호 시점에 견적한다.

## 3. ERP 판매 테넌트 분리 — 이미 정한 것 위에 얹는다

| 항목 | 지금 | 판매 때 필요한 것 |
|---|---|---|
| 데이터 분리 | 모든 표에 `tenant_id`(기본 wellperion) · 조회는 항상 tenant 로 거른다 (장기결정 #3) | 변경 없음 |
| 로그인 분리 | erp-auth `users.tenant_id` · 역할(admin/직원) · 권한 칸 | 변경 없음 |
| 상담봇 분리 | 테넌트 = 폴더 1개(`faq/{tenant}/`) + nginx 경로 1줄 — 다캠·스포짐으로 실증 | 새 테넌트마다 같은 3줄 |
| 3얼굴 | 직원앱(`/erp/` 로그인 사용자) · 회사관리자(테넌트 안 role=admin) = 있다 | **슈퍼관리자(테넌트를 넘나드는 자리)만 없다** — 신규 생성이라 GM 승인 뒤 만든다 |
| 핵심 3모듈 | 회원·문의·점검 서버 원천 전환 = 배1039 진행 중 | 1039 가 끝나면 판매 단위가 서버 위에 완성된다 |

새 테넌트 1곳 추가 = FAQ 폴더 1개 + 계정 1행 + nginx 경로 1줄. 코드 변경 없음.

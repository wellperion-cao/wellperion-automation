### 1-5. 30분 전 알림 — 이미 존재하는 배선의 정확한 모습

`telegram_bot/daily_scheduler.py:3082-3146` `_run_meeting_reminder()`:

- 트리거: 상주 스케줄러(WellperionDailyScheduler 예약작업으로 부팅 시 기동)의 **5분 주기** 잡 `meeting_reminder_30min`(3531-3538행). 배451 · GM 확정 2026-08-07, 목적지를 카톡→텔레그램 하루방으로 이전 2026-08-18 배691.

- 발신: 시작 27~33분 전 창(±3분 허용)에 들어오면 `tg_outbound_log.send` **기존 관문 하나로만** 발신, GM업무 화면 링크 포함.
- 중복 방지: 관문의 방+내용 서명 2시간 창 + 프로세스 내 `_MEETING_REMIND_SENT` 집합.
- 시각 없는 일정: 계산 불가라 제외하되 **제외 사실을 로그에 남긴다**(3117-3119행 · 조용한 누락 금지).

## 2. '30분 전 알림'을 어디에 얹나 — 후보 비교와 결론

| 후보 | 주기 | 판정 |
|---|---|---|
| **A. 상주 daily_scheduler 의 기존 `meeting_reminder_30min` 잡** | 5분 | **채택** — 이미 정확히 이 목적으로 만들어져 live 로 돌고 있다. 새로 얹을 것 자체가 없다 |
| B. Wellperion-CPO-Inquiry-Snapshot-3min 에 절 추가 | 3분 | 기각 — CPO 문의 도메인에 GM 개인 알림을 섞으면 모듈 경계가 무너진다(약속 L23 취지) |
| C. Wellperion-CMO-Content-Intake-15min 에 절 추가 | 15분 | 기각 — 15분 주기는 ±3분 허용창(27~33분 전)을 그냥 지나칠 수 있다 |

채택 이유 한 줄: **이미 있는 것이 정답이다** — 5분 주기라 30분 전 창을 놓치지 않고, 발신 관문·중복 가드·실패 로그까지 갖춰져 있다(약속 L21 "정본 먼저 확인").

**시각 없는 일정(날짜만 있는 항목)의 처리 — 현행 유지:**
- 30분 전 계산이 불가능하므로 리마인드 대상에서 빼되 제외 로그를 남긴다(현행 코드가 이미 그렇게 한다).
- 대신 그 항목들은 **08:00 아침 브리핑의 「오늘 잡힌 일정」 절**이 전부 싣는다 — 날짜 단위 항목의 리마인드는 아침 브리핑이 담당한다는 역할 분담을 이 설계서로 명문화한다. 시각을 지어내 30분 전을 계산하는 일은 하지 않는다(약속 L23 "빈칸을 지어 채우지 않는다").

### 2-6. 발견한 틈 1건 (이번 설계에서 유일하게 알림 쪽에 손댈 후보)

`_filter_today_items()` 는 **assignee 에 'GM'/'김남욱'이 든 건만** 리마인드한다(gm_checkin.py:101-103). 그런데 카톡 다리(`bridge_to_schedule`)로 들어온 일정은 assignee 칸에 LLM 판독의 dept 값(실무진 이름일 때가 많음)이 들어간다(ops_daily_digest.py:1496-1503). **GM 이 직접 가야 하는 미팅이 카톡에서 자동 등록되면 assignee 에 '김남욱'이 없어 30분 전 알림이 안 울릴 수 있다**(추정 — 실제 미발신 사고 사례는 미확인). 대응은 §4 2단계에 적는다. 새 판정 로직을 만들지 않고 기존 함수의 필터 한 줄 문제라 수정 반경이 작다.

## 3. 모듈 하나의 경계 — 무엇이 안이고 무엇이 밖인가

```
[모듈 안 — GM 하루 파이프라인 (배선 계층)]
  입력  : 카톡 방 발화 → 07:30 digest bridge_to_schedule → 전사일정 GAS
          사람 직접 입력 → 전사_일정.html 편집(8칸) → 전사일정 GAS
          AI 등록 → scripts/schedule_ssot.add_event() (중복가드+GAS 동시반영)
  표면  : 08:00 아침 브리핑(4소스 병합) · 20:30 저녁 정리 → 「하루」 방
          GM업무.html (+ 1단계로 「오늘 일정」 띠)
  알림  : meeting_reminder_30min (5분 주기 · 30분 전 · 「하루」 방)

[모듈 밖 — 데이터를 소유한 기존 모듈 (가리키기만, 복사 금지 · 약속 L01)]
  coo-schedule-ssot      : 전사일정 데이터 자체 (GAS + schedule_ssot.json)
  cto-ops-morning-digest : 07:30 카톡 다이제스트 생산 (bridge 는 그 산출을 이 모듈 입력으로 쓴다)

```

경계 원칙: **이 모듈은 데이터를 소유하지 않는다.** 데이터 정본은 기존 두 모듈에 그대로 두고, 이 모듈은 "GM 이 놓치지 않게 하는 배선"(병합 표면 + 사전 알림)만 소유한다. 같은 판정 로직을 두 곳에 두지 않는다 — 오늘자 GM 담당 선별은 `gm_checkin._filter_today_items` 하나뿐이고, 화면(1단계)도 같은 GAS 원천을 읽되 판정은 단순 표시(오늘자 필터)만 한다.

## 4. 가장 작은 1단계 (하루 안에 끝나고 되돌릴 수 있는 것)

**1단계: GM업무.html 상단에 「오늘 일정」 띠 1개.**

- 내용: 페이지 로드 시 `SCHEDULE_GAS_URL?action=load_schedule` 을 fetch(전사_일정.html 이 이미 쓰는 같은 GAS·같은 액션 — 새 GAS·새 액션 0), `next_due === 오늘` 항목을 시각순으로 한 줄씩 표시(시각 없으면 "종일"). 실패 시 "전사일정을 불러오지 못했습니다" 한 줄(0건과 못 읽음 구분 — 자가점검 7번).
- GM 화면에 달라지는 것 한 줄: **GM업무 화면을 열면 맨 위에 오늘 일정(시각·제목)이 뜬다 — 전사일정 화면을 따로 열 필요가 없어진다.**
- 변경 반경: HTML 1개 파일, 커밋 1개. 데이터·GAS·스케줄러 무변경.

**2단계(1단계 검증 후 · 별도 승인):** §2-6 틈 — 30분 전 리마인드 대상 선별에서, 카톡 다리로 들어온 항목 중 GM 참석 건이 빠지는 문제. 안 = `bridge_to_schedule` 판독 프롬프트에 "GM(김남욱) 참석 건은 assignee 에 '김남욱 GM' 표기" 지시 한 줄 추가(판정 함수는 안 건드림 — 데이터가 규격을 맞추게 한다). 실제 미발신 사례 실측 후 진행.

**3단계(선택 · GM 결정 대기):** 모듈 등록(§3 초안) + notify_registry 참조 표기.

## 5. 위험과 되돌리는 법

| 위험 | 정도 | 되돌리는 법 |
|---|---|---|
| 1단계 띠가 GM업무 화면 로드를 느리게 함 | 낮음 — 기존 readPlan·CHECK_GAS fetch 와 병렬, 실패해도 나머지 섹션 무영향으로 설계 | `git revert <1단계 커밋>` 1회 — 데이터 무변경이라 이것으로 완전 원복 |
| GAS 응답 지연·실패 시 빈 띠 | 낮음 | 실패 문구 표시(조용한 실패 금지). 원복 불요 |
| 모듈 등록이 기존 coo-schedule-ssot 와 겹쳐 보임 | 낮음 | feature 문구에 "데이터 소유 없음·배선만" 명시(초안 반영됨). 겹침 지적 시 등록 항목 1건 삭제로 원복 |
| 2단계 프롬프트 수정이 판독 품질을 흔듦 | 중간 | 프롬프트 한 줄 revert. bridge 는 하루 3건 상한·중복 가드가 있어 오염 폭이 제한됨 |
| 30분 전 알림 이중 발신 | 이미 방어됨 | 발신 관문 2시간 서명창 + 프로세스 내 기억(현행 코드) — 이 설계는 발신 경로를 안 건드림 |

**전체 원상복구 절차:** ① GM업무.html 커밋 revert → ② module_registry.json 항목 1건 제거(넣었다면) → ③ notify_registry 표기 원복(넣었다면). 스케줄러·GAS·데이터 파일은 이 설계에서 한 번도 변경되지 않으므로 복구 대상이 아니다.

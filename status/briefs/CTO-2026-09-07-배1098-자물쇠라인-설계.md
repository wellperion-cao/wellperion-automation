# 🔒 자물쇠 라인 설계 — AWS 최신버전 외 수정·데이터 이관 커밋의 푸시 GM 승인 관문 (배1098 · 시토 · 2026-09-07 · 웰리 검토용 1장)

GM 원문(웰리 창 10:3x): 「AWS 최신버전 외에 수정 및 데이터 이관 관련해서는 자물쇠라인이 하나 있어야 · 커밋 푸시 관련 나한테 승인을 당분간 받는 모듈 · 권한 페이지에 계정 승인처럼 커밋 푸시 승인도」.

## 1. 원칙 — 새 장치를 늘리지 않는다(약속 L21)
- **커밋은 막지 않는다. 푸시를 막는다.** 서버는 매분 `git pull` 이라 푸시 = 배포. 로컬 커밋은 일감 보존용으로 그대로 둔다.
- 판정·요청·차단은 **이미 모든 세션이 지나가는 관문 하나** = `scripts/safe_commit.py` 의 push 단계(post_commit_push 호출 직전). 맨손 `git push` 는 `.git/hooks/pre-push` 가 같은 판정 함수를 부른다(접수처 잠금이 pre-commit 을 쓰는 것과 같은 짝).
- 잠금 정본 = **`status/push_lock.json` 한 파일**(접수처 `reception_freeze.json` 과 같은 모양): `locked` · `paths` · `unlocked_by`. GM 이 「자물쇠 해제」라고 하면 그 세션이 false 로 바꾸고 원문·일시 기록. AI 가 스스로 풀지 않는다.
- 승인 기록 = **`status/push_approvals.json`** 한 파일(요청 행 = id · sha · 경로 · 요약 · 요청 역할 · 상태 pending/approved/rejected · GM 응답 시각). 승인 카드·화면·푸시 판정이 전부 이 파일만 읽는다.

## 2. 잠그는 경로(대상 = 「서버 원천·데이터 이관을 바꾸는 파일」)
| 묶음 | 경로(prefix/glob) | 왜 |
|---|---|---|
| 서버 코드·배포 | `server/**` (erp_api·erp_auth·erp_chro·common/schema.sql·deploy_*.sh) | API·DB 스키마·서비스 = 원천 자체 |
| 동기화·되밀기·대조 | `scripts/sync_*.py` · `scripts/pushback*.py` · `server/erp_api/reconcile_*.py` · `scripts/origin_switch*` | 시트↔서버 데이터 흐름 |
| 원본 스위치·이관 실행 | `status/origin_switch*.json` · `scripts/*migrat*.py` · `scripts/*import*.py` · `status/backups/**` 삭제 | 어느 쪽이 진실인지 바꾸는 손잡이 |
| GAS 배포본 | `.deploy-*/**` | GAS 코드 변경 = 시트 쪽 원천 변경(09-07 8월 시트 오기입도 여기서) |
| 공식값·규약 | `ssot/**` | 공식값은 원래 GM 결재 영역 |
| 화면의 원천 전환 | `3. 웰페리온 가이드/**/*.html` 중 diff 에 `script.google.com/macros` · `/api/` · `apiFirst` · `ERP_API_ON` 이 **추가·삭제되는 커밋만** | 화면 문구 수정까지 잠그면 실무진 화면이 멈춘다 — 원천 호출이 바뀌는 줄만 |
| 잠그지 않음 | `status/_queue.json`·worklog·briefs·logs·heartbeats·콘텐츠·문서 | 데이터 원천과 무관(AI 살림·기록) |

「AWS 최신버전 자체는 자율」 = 위 경로라도 **서버가 이미 원천인 표의 버그 수리·성능·로그**는 GM 이 풀어 둔 기간엔 자율 — 판정은 사람이 아니라 경로로만 하므로, 그 구분은 잠금 파일의 `allow_globs`(예: `server/erp_api/api_check.py`) 로 GM·웰리가 넓힌다. 처음엔 비워 둔다(전부 승인).

## 3. 흐름
1. 세션이 `safe_commit.py` 로 커밋 → push 직전 판정: 커밋에 잠금 경로가 섞였나? (없으면 종전대로 즉시 푸시)
2. 섞였으면 **푸시 안 함** + `push_approvals.json` 에 요청 행 + GM 개인 봇방 카드 1장(요청자·경로·요약·[승인]/[반려] — 기존 `wrk:` 콜백 카드 재사용 · 새 발신기 없음) + 셸에 「승인 대기(요청 id)」 한 줄.
3. GM 이 카드에서 승인 → 봇이 파일 상태 approved → 이미 도는 `daily_scheduler._push_sweeper`(5분)가 approved 커밋만 `git push`(요청 sha 가 HEAD 조상인지 확인 · 뒤에 잠금 커밋이 또 있으면 그것도 요청 대기). 반려 → 그 커밋은 로컬에 남고 세션이 되돌린다(`git revert` 로 새 커밋 · reset 금지).
4. 화면 = ERP 권한 관리 페이지(배1026)에 **「커밋·푸시 승인」 탭** — 계정 승인 탭과 같은 표(요청 시각·역할·경로·요약·[승인][반려]) · 원천 = `/api/push_approvals`(읽기) + `/api/write` 관문의 액션 하나(쓰기 · GM 계정만). 봇 카드와 화면은 같은 파일을 고치므로 어느 쪽에서 눌러도 같다.
5. 서버 매분 pull 은 그대로 — 푸시가 안 되니 배포도 안 된다. 서버 쪽 scp 직배포(`deploy_*.sh`)도 같은 판정을 부른다(잠금 경로면 승인 id 없이는 실행 거부).

## 4. 실무진·운영 영향
- 실무진 화면 변화 없음. 늦어지는 것 = 잠금 경로 변경분의 배포(GM 승인까지). 긴급 장애 수리는 GM 카드 한 번 = 1분.
- 웰리·시토 세션은 승인 대기 중에도 다음 배를 진행(커밋은 쌓이고 푸시만 대기).

## 5. 구현 순서(가역 · 시토 · 배1026 같은 세션)
1. `status/push_lock.json` + `push_approvals.json` 스키마 · `safe_commit.py` 판정+요청+카드 · `.git/hooks/pre-push` · `_push_sweeper` 승인 푸시 (반나절)
2. 권한 페이지 탭 + `/api/push_approvals` (반나절)
3. GM 첫 승인 실측 1회(더미 커밋 아님 — 실제 잠금 경로 커밋 1건으로) → 배 note 증거.

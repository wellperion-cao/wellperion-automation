## ② 미러 유무·필요한 새 미러
- **DB 동기 미러(sync_reception.py류) 없음.** 대신 **인메모리 "마지막 정상본"**(`api_reception_ops._LAST`, 프로세스 재시작 시 소실, 최대 32칸)만 있다.
- 읽기는 **매 요청 GAS 로 실제 왕복**한다 — GAS 부하·지연·구글 안내HTML 리스크는 09-04 이전과 동일. 서버는 통로+감사로그 역할만.
- 신규 DB 미러는 **권장하지 않는다.** 이유는 `api_reception_ops.py` 주석에 이미 명시: 30초 자동새로고침+즉시 셀편집이라 주기 동기(5분류 sync_*.py 패턴)를 앞에 두면 "방금 옆자리가 고친 값이 되돌아간 것처럼" 보인다. 이 판단은 09-04 설계 당시 이미 내려졌고 지금도 유효하다.
- 진짜 남은 공백 1개: 마지막 정상본이 **RAM 전용**이라 배포·재시작마다 사라진다. 디스크(JSON 파일 또는 SQLite 1행) 로 옮기면 재시작 직후 첫 실패 때도 안내가 가능 — 이것도 스키마 변경 없는 저위험 보강이라 "미러"라기보다 저장소 이동 수준.

## ③ 읽기 미러 전환 순서 (이미 1·2단계 완료 · 시토 관측)
1. **완료(09-04)** — 읽기: 화면 → 서버 `/api/reception-ops` → GAS 그대로 왕복, 실패 시에만 서버가 마지막 정상본 대체. 되돌리기: `_assets/erp_write.js` 의 `erpRcPost` 를 화면에서 안 부르고 원래 `fetch(state.url,...)` 로 바꾸거나 `ERP_ON` 조건을 false로.
2. **완료(09-04)** — 쓰기: 화면 → 서버 `/api/write` → write_log 이중기록 → GAS 전달, 실패 시 화면이 GAS 로 1회 직접 재시도. 되돌리기: 위와 동일(`erpRcPost` 되돌리기가 읽기·쓰기 공통).
3. **미착수·저위험 보강(제안)** — 마지막 정상본을 RAM에서 디스크(SQLite 1테이블 또는 JSON)로 이전. 되돌리기: 파일 삭제하면 자동으로 09-04 RAM 방식과 동일 동작(코드가 파일 없으면 빈 상태로 시작).
4. **미착수·신규 인프라(별도 배 · GM 승인 필요)** — GAS 를 완전히 은퇴시키려면 `origin_switch.WRITE_AREA` 에 리셉션·라커 항목을 추가하고 DB 를 원본으로 쓰는 `pushback.py` 대상에 9+3개 탭을 편입해야 한다. 지금은 이 스위치가 없어 모든 쓰기가 항상 GAS 로 동기 전달된다(`server_mode` 판정 불가).

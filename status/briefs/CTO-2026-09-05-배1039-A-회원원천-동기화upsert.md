## 0. 전제 — sync_*.py 통째 DELETE→INSERT → upsert 전환

오늘 실사고 C1(sync_reception.py `_replace`)과 같은 부류를 전수 점검했다. 결과:

| 파일 | 상태 | 조치 |
|---|---|---|
| sync_reception.py | 오늘 이미 수리(다른 레인) | 손 안 댐 |
| sync_inquiries.py | 통째 DELETE→INSERT | **diff삭제(이 배치에 없는 id만)+upsert 로 전환** |
| sync_members.py | 통째 DELETE→INSERT(scope별) | **diff삭제(이 배치에 없는 회원번호만)+upsert 로 전환** |
| sync_todo.py | 통째 DELETE→INSERT(todo_items·approvals) | **diff삭제(이 배치에 없는 id만)+upsert 로 전환**, INSERT 도 ON CONFLICT DO UPDATE 추가 |
| sync_board/check/misc/sales/funnel/brojay/lesson.py | 이미 행 단위 upsert(ON CONFLICT), 통째 DELETE 없음 | 손 안 댐 |
| sync_kakao.py | 통째 DELETE→INSERT(kakao_rooms) | **의도적으로 유지** — 서버 직접쓰기 경로가 없다(api_kakao.py 는 GET 전용). GAS 가 유일한 원천이라 방 삭제도 그대로 반영돼야 한다(diff삭제로 바꾸면 지워진 방이 안 지워지는 역행). |

방식: 이번 GAS 배치에 있는 키는 upsert(ON CONFLICT DO UPDATE), 배치에 없는 키만 DELETE — 서버가 그 표에 직접 쓰기 시작해도 그 행의 키가 다음 배치에도 있는 한 사라지지 않는다. 배치가 통째로 비면(원천 조회 이상) 예전처럼 전량 삭제하지 않고 안전하게 스킵.

검증: 3개 파일 selftest 통과(서버 실제 PostgreSQL) → 서버 배포 → 수동 실행 1회 → 행수 대조.

|---|---|---|
| inquiries | 2554 | 2554 |
| members | 1746 | 1746 |

## ① 회원 원천 전환 — 실사 결과, 쓰기는 아직 전환 못함(막힘 · 사유 명시)

**읽기는 이미 서버 우선.** `/api/members`·`/api/members/summary`·`/api/members/{no}`(app.py) + `/api/report/*`(members_report.py, 배943) 전부 PostgreSQL `members`/`inquiries` 미러를 직접 읽는다. 시트는 안 건드린다.

**쓰기는 여전히 GAS 가 먼저다.** `api_write.py`(`_MEMBER_WRITES` 7종: member_active_update·member_owner_save·member_registered_add·member_registered_remove·member_archive_restore·member_hold_transition·member_hold_approve)는 지금 payload 를 **GAS 로 포워드(원본 저장) → 성공하면 sync_members.py 를 즉시 재실행**하는 구조다. "서버 원장에 먼저 적고 시트는 write-through 사본" 으로 뒤집으려면 이 7종 각각의 실제 저장 로직(지문 대조 저장·행 삭제+신규행·이용일수 증분·상태 전이 등, `.deploy-funnel-v2/Survey.js` 4300~10800행대)을 PostgreSQL 트랜잭션으로 재구현해야 한다.

**막힌 이유:** 실제 회원 1,746명 데이터가 걸린 쓰기 로직 7종을 이 세션 한 번에 재구현하는 것은 검증 없이 밀어붙이면 오히려 위험하다(회원번호 충돌·이력 훼손 가능). GM 이 이미 세운 `reconcile_dual_write.py`(배960)의 "이중기록 3일 연속 무결 → 사람이 전환 판단" 게이트가 바로 이 위험을 막으려고 만든 절차다. 회원 쓰기 경로는 그 게이트 밖에 있다(현재 대조 대상은 inquiry·reception·write log 뿐, members 표 자체의 쓰기 대조는 없음).

**다음 담당·순서 제안:** 회원 쓰기 7종을 하나씩(가장 단순한 것부터 — 예: member_owner_save 담당자 저장 1칸) PostgreSQL 직접쓰기 + GAS 로 비동기 write-through 복사 → 3일 대조 무결 확인 → 다음 액션. 시토가 이어서 진행(1039 note 에 진척 기록).

## 1. 🔴 문의 즉시 알림 사망 — 최우선

### 증상
새 문의가 들어와도 **즉시 알림이 나가지 않는다.** 어제 문의 3건(김화연 08:33 · 임유진 09:00 · 윤은혜 17:14) 전부 발송 기록 없음.

### 실측 (기존 읽기전용 액션 `diag_inquiry_state`)
```
triggers      : []      ← ScriptApp.getProjectTriggers() 전수. 필터 아님
INQ_LASTROW   : null    ← 문의 시트 8개 전부
```

- `onInquiryFormSubmit`(즉시) · `_notifyNewInquiries_`(5분 폴링) **둘 다 트리거 0개**
- 이중 설계인데 **양쪽 다 안 돈다**

### "남의 계정 트리거일 수도" 반론이 안 통하는 이유
`getProjectTriggers()`는 호출 계정 소유분만 본다. **그런데 마커가 닫는다.**
즉시 핸들러(`Survey.js:1027`)도 폴링(`:851`)도 실행되면 ScriptProperties의 `INQ_LASTROW`를 갱신하는데,
**ScriptProperties는 계정 공유**다. 8개 시트 전부 null = **어느 계정으로도 한 번도 안 돌았다.**
최초 실행이면 baseline이라도 찍힌다(`:1005`).

### ⚠️ 심각도는 '중상'이다 — 전면 사망 아님
시포가 GAS 밖을 확인한 결과 **다른 경로가 살아있다**:

| 경로 | 상태 |
|---|---|
| 즉시 알림 | 🔴 죽음 |
| **매일 22:30 문의 다이제스트** (`telegram_bot/daily_scheduler.py:3669`) | 🟢 살아있음 |
| ERP 화면 노출 | 🟢 정상 (강습 최근30일 142/142 확인) |

→ **문의가 사라지는 게 아니라 반응이 최대 하루 늦는다.** 다만 구글폼이 문의의 91%를 받으므로 영향 범위는 넓다.

### ★복구 시 함정 — 이게 이 건의 핵심 리스크
**트리거만 덜컥 설치하면 마커가 null이라 과거 623건이 한 번에 발송된다.**
코드에 폭주 방지 주석이 이미 있다(`Survey.js:1146`).
→ **설치 전 baseline 마커 선세팅 필수.** 어디를 기준점으로 잡을지가 판단 지점.
→ 누락분 수동 발송 경로는 이미 있다(`:2222`, 1건씩·마커 불변).

### 확인 한 방
실무진에게 **"문의 알림 요즘 오나요?"** 한 마디면 즉답이 나온다.

## 3. 🟠 `_mirrorInquiryToStaffLog_` — 빈 행 아래에 꽂는 버그

`Survey.js:256`
```js
sh.getRange(sh.getLastRow() + 1, 1, 1, lastCol).setValues([newRow]);
```

`getLastRow()`는 **서식만 남은 빈 행까지 센다.** 그래서 CTA 웹폼 미러 건이 빈 행 76개를 건너뛰고 그 아래에 꽂힌다.

**이 코드베이스가 스스로 금지해둔 패턴이다** — `Survey.js:821`:
> `★ getLastRow()(빈행포함) 금지 — 실데이터 기준 _realLastDataRow_ 사용`

알림 경로는 `_realLastDataRow_`를 쓰는데 **미러 경로만 안 쓴다.**
행 손실은 아니고 **위치가 어긋나는** 문제(화면엔 정상 노출).

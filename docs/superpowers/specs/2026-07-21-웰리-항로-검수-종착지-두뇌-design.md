# 웰리 항로 검수·종착지 두뇌 (Hangro Review & Destination Brain) — 설계

- **작성일:** 2026-07-21
- **소유:** 웰리 (AI CEO) — 두뇌·판단. 엔진(구현)=시토(CTO)/executor 위임.
- **상태:** 설계 확정(GM 승인 2026-07-21) → 구현 계획 대기
- **관련 배:** 자율화 배237(GM 보좌) 산하 · 북극성 추천기(Wellperion-NorthStar-0630) 진화

---

## 1. 목적 (한 문장)

웰리가 **모든 배를 순회하며 ① 상태가 정직한지 검수하고 ② 종착지(다음 한 수 + 최종 북극성)를 생성해 ③ 배별로 GM께 즉시 핑** → GM 승인 시 항로에 반영하는 **단일 두뇌 모듈**.

### 배경 (GM 문제 인식)
- 기존 북극성 추천(06:30 생성 → 08:00 브리프 자동 흡수)은 **GM 결정 루프가 없다** — 자동으로 흘러갈 뿐.
- GM이 항로에서 목격: *"입항된 줄 알았는데 대기·진행중에 엉뚱하게 남아있는 배들"* = **상태 정직성이 깨진 배**들이 있다.
- 비슷한 맥락의 루프·모듈(북극성 추천 / 표류 감지 / next 촉구)이 흩어져 있다 → **하나의 제대로 된 모듈로 통합**하고, **당분간 GM이 함께 판단·결정**하게 만든다.

| 층 | 대상 | 시점 | 지금 | 새 모듈에서 |
|---|---|---|---|---|

## 4. 흐름 (검수 → 생성 → 핑 → 반영)

```
① 검수(Audit)   큐 전 배 순회 → 각 배 "상태 정직성 판정" + 종착지 유무
② 생성(Generate) 종착지 필요·의심 배마다 → LLM 두뇌로 [다음 한 수 + 최종 북극성] 생성
③ 핑(Ping)       배별 카드 → GM (텔레그램 승인라인 재사용, 중복·연발 방지)
④ 반영(Apply)    GM 승인 → 기존 --next 배관으로 next·종착지 기록 → 항로보드 🔗 렌더
```

### 4-1. 검수(Audit) 판정 규칙 — GM이 짚은 "엉뚱한 상태" 잡기

각 배의 **상태값 vs 실제 신호**를 대조해 ⚠️ 의심 배를 분류한다:

| 판정 | 조건 | 제안 |
|---|---|---|
| `done_look_not_done` | note/next가 "완료·입항"인데 status ∈ {PENDING, IN_PROGRESS} | 입항 확정 or 진짜 남은 일 명시 |
| `stale` | `updated_at` 무변동 N일 (무게별 ⛵2/⛴️3/🛳️5일, `stall_watch` 재사용) | 정박(대기) 전환 or 재개 |
| `drift` | DONE + source=queue + next 빈값 + 후속 PENDING 없음 (`hangro_board._classify` 재사용) | 종착지 생성 |
| `mislabel` | STANDBY/대기인데 최근 활동 흔적 | 진행중 승격 |
| `no_destination` | 활성인데 최종 북극성 연결 없음 | 북극성 종착지 부여 |

### 4-2. 생성(Generate) — LLM 두뇌

- 입력: 배 1척의 문맥(title·note·priority·module·owner 북극성·KPI).
- 출력(JSON): `{ next_step, final_destination(=어느 북극성), path_map(🌟→📍→👉), confidence }`.
- 1순위 `brain_claude_cli`(claude CLI, API 크레딧 0) / 2순위 규칙 폴백. (북극성 추천기 방식 그대로.)
- **정직성(중요):** LLM `confidence` < 임계값이면 **"저확신 제안"** 라벨로만 — 단정 금지. 지어낸 종착지 금지(L05).

## 5. GM 결정 UI (당분간 함께 결정)

- **카드 1장 = 배 1척:** `제목` · `검수 결과(⚠️ 왜 짚였나)` · `웰리 추천 종착지(다음 한 수 + 최종점)` · **[승인] [수정] [반려]**.
- 승인 → 즉시 항로 반영 / 반려 → 사유 기록·재핑 안 함 / 수정 → GM 문구로 덮어씀.
- 아침 06:30 역할 추천(층 A)도 **같은 카드 형식** → GM이 하루 판단을 한 곳에서.
- 채널: 텔레그램 승인라인(기존) 재사용 + (후속) G1 항로 보드 검수 패널.

## 6. 보완점 (과거 사고 메모리 기반 방어) — 필수

1. **중복 누적 방지(dedup):** 배별 결정 원장(`status/hangro_decisions.jsonl`)에 stable key(=ship_no + 문맥 해시) 기록. **GM이 결정한 배는 재핑 안 함**, 문맥이 실질 변할 때만 재제안. (gm_aide `unapproved dedup` 날짜누적 역설 재발 금지 — `feedback` 메모리.)
2. **텔레그램 연발(429) 방어:** "배별 즉시" = 다음 폴 틱 안에서 **간격 제어 큐잉**. 다발 발송 금지 (`reference_telegram_burst_send_flood`).
3. **거짓 종착지 금지:** confidence 라벨링·저확신은 제안 표기, 지어내기 금지(L03·L05).
4. **비파괴 라이브:** 06:30/08:00 기존 배선을 그림자 검증 전엔 **건드리지 않음**. 자율 쓰기는 게이트 뒤(`HANGRO_APPLY` 기본 OFF, 반영은 GM 승인 후에만).
5. **가역성 게이트(자율화 경로):** 지금 = 제안만(GM 결정). 이후 신뢰 쌓이면 **가역적 종착지 쓰기만** `HANGRO_APPLY=1`로 자율 반영(AIDE_*_APPLY 선례). 비가역·전략은 항상 제안만.
6. **큐 직접쓰기 최소화·직렬화:** 추천은 pending 원장에 저장, `_queue.json` next 반영은 **승인 시에만** 기존 `clevel_post_action --next` 배관으로(동시커밋 손상·임시인덱스 함정 메모리 준수).
7. **검수 자체는 read-only:** Audit 단계는 상태를 **바꾸지 않고 판정만** → GM 승인으로만 상태 전환(입항 확정 등). 자동 상태변경 금지.

## 7. 안전 전환 (그림자 → 승격 → 정리)

- **Phase 0 (빌드·그림자):** 새 모듈 작성 + `--dry-run`. 기존 크론 무변경, 델타 0 확인(게이트 OFF). pytest.
- **Phase 1 (GM 결정 카드 라이브):** 배별 종착지 핑 + 06:30 역할 추천 카드 승격. 반영은 GM 승인 게이트.
- **Phase 2 (정리):** 겹치는 옛 조각 은퇴 — `gm_aide` next_augment 촉구 placeholder 제거, 북극성 추천기 두뇌는 새 모듈에 흡수·재배선. 중복 크론 통합.

## 9. 성공 기준

- GM이 항로에서 **"엉뚱한 상태"** 배를 카드로 통보받고 한 번에 정리 가능.
- 각 배가 **다음 한 수 + 최종 북극성**을 갖는다(표류 0 지향).
- 흩어진 3조각(북극성 추천·표류감지·next촉구)이 **하나의 모듈**로 수렴, 중복 크론 감소.
- GM 개입은 **결정만**(생성·검수·반영 기계화), 신뢰 쌓이면 가역 건 자율.

## 10. 비목표 (YAGNI)

- 배 **실행**(welly_auto_runner 영역)은 흡수하지 않음.

- 완전 무인(당분간 GM 함께 결정 — 신뢰 후 단계 확대).

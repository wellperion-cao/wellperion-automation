# 문의회원 읽기 성능 — 서버 스냅샷 가속 설계 (2026-07-16, 시토)

## 배경·목표
`3. 웰페리온 가이드/cpo/member/문의회원.html`(실 상담사 프로덕션)의 첫 진입·모든 기기에서 대기시간을 0초로 만든다.
기존에 이미 있는 것: localStorage stale-while-revalidate 캐시(멤버십 `cpo_iq_db_cache_v1`, 강습
`cpo_iq_lesson_cache_v1_{type}_{scope}`, 5분 TTL) — 단, **첫 진입·다른 기기**에는 캐시가 없어 여전히 gviz
~1초(멤버십) 또는 GAS 6~9초(강습 scope=all) 대기.

**★절대 우선순위(GM 명시) = 유실 0.** 속도 개선은 이 원칙을 해치지 않는 범위에서만 진행한다.

## 아키텍처 — 3층 렌더 파이프라인
```
1층 서버 스냅샷 (신규)     : status/inquiry_snapshot_member.json, status/inquiry_snapshot_lesson.json
                              — 2~3분 주기 예약작업이 GAS를 조회해 rows를 그대로 덤프. git 커밋·푸시.
                              — raw.githubusercontent.com 을 통해 페이지가 즉시 fetch(기존 여러 페이지가
                                쓰는 검증된 패턴, RAW_BASE 관례 그대로 재사용).
2층 localStorage 캐시 (기존): 같은 기기 재방문 시 최우선(가장 빠름, 네트워크 0회).
3층 gviz/GAS 라이브 재검증 (기존, 무조건 발사): 1·2층 중 무엇으로 첫 렌더했든 상관없이 항상 실행 —
                              진실은 이 계층. 완료 시 화면을 최신으로 교체.
```
렌더 우선순위(각 loadDbData/lessonLoad 호출마다):
1. localStorage 캐시 있음 → 캐시로 즉시 렌더(기존 동작 그대로, 최우선 — 네트워크 0회라 스냅샷보다 빠름).
2. 캐시 없음(첫 진입·새 기기) → 서버 스냅샷 fetch(1회 왕복, 통상 <200ms) 성공 시 그걸로 즉시 렌더.
3. 스냅샷도 없거나 실패 → 기존처럼 "불러오는 중…" 스피너.
4. 위 세 경로 중 무엇이었든, **1·2·3층 렌더와 무관하게 gviz/GAS 배경 재검증은 항상 무조건 발사**(기존
   `loadDbData`/`lessonLoad`의 `_dbPromise`/`_lessonPromise` — 조건 추가 없이 그대로 유지). 도착하면
   `dbRows`/`st.rows`를 교체하고 다시 렌더 — 이게 최종 진실.

## 유실 0 게이트 — 설계상 보장 방법
| # | 게이트 | 보장 방법 |
|---|---|---|
| 1 | 배경 gviz 재검증 항상 발사 | `loadDbData`/`lessonLoad`의 기존 `_dbPromise`/`_lessonPromise` 흐름은 **1줄도 조건부로 만들지 않음** — 스냅샷 렌더는 그 위에 "먼저 보여주기"만 얹는다. 스냅샷 fetch가 아무리 늦거나 실패해도 재검증 fetch는 함수 진입 시점에 이미 예약됨. |
| 2 | 신선도 ts 투명 표시 | 스냅샷·캐시 렌더 시 `dbCount`/`lessonStatLine`에 "N건 · {X}분 전 기준 · 갱신 중…" 표기(스냅샷 파일의 `generated_at_kst`/캐시의 `ts` 사용). 실제 gviz/GAS 응답 도착 시 원래 문구(신선도 접미사 없음)로 자동 복귀. |
| 3 | WriteBuffer 오버레이 보존 | 스냅샷 렌더 경로도 캐시 경로와 동일하게 `WriteBuffer.applyOverlay(rows, scope)` 통과 후 렌더(신규 분기 추가 안 함, 기존 함수 그대로 재사용). 매칭 키는 `row.phone`(digits-only) — 스냅샷 row도 GAS 원본 shape 그대로라 100% 동일. |
| 4 | INC-013 제약 | 스냅샷 rows는 GAS `member_inquiry_list`/`lesson_inquiry_list` 응답을 **그대로 통과**(재가공 없음) — rowIndex 신뢰 금지·keyPhone 물리행 복구는 이미 백엔드(Survey.js)가 저장 시점에 담당하는 불변 계약이라 스냅샷이 개입할 지점이 없음. 저장 성공 판정도 기존 `apiPost` ok:true 로직 무변경. |
| 5 | 스냅샷 job 실패 시 fallback | (a) 스냅샷 fetch 자체가 실패/404/파싱오류 → catch로 흡수, `console.warn` 로그 남기고 조용히 3단계("불러오는 중…")로 폴백 — 사용자 토스트 없음(비필수 가속층 실패는 소음 아님). (b) 스냅샷 **생성 job**이 죽어도 페이지는 몰라도 됨 — 그냥 파일이 stale해질 뿐, gviz/GAS 재검증은 무관하게 계속 정상 작동. (c) job 자신도 GAS 호출 실패 시 직전 스냅샷 파일 내용을 그대로 carry-forward(빈 값으로 덮어쓰지 않음) + `warnings[]`에 기록 + 로그 파일에 남김(조용한 실패 금지). |
| 6 | 수동 새로고침=항상 최신 | 새로고침은 브라우저 재파싱이라 위 1~5가 매번 처음부터 재실행 — 결국 무조건 gviz/GAS 재검증을 다시 거친다. 기존 새로고침 시 캐시 우선 로직과 동일 원칙이라 변경 없음. |

## 서버 스냅샷 job — `scripts/cpo_inquiry_snapshot.py`
- **데이터 소스 결정: gviz 포팅이 아니라 GAS 재사용.** 최초 검토는 문의회원.html의 gviz 어댑터
  (`gvizMiRows_`/`gvizLessonRows_`, ~150줄 헤더매칭·포맷 로직)를 Python 1:1 포팅하는 안이었으나,
  **`scripts/cpo_report.py`가 이미 동일 GAS 엔드포인트(`FUNNEL_EXEC_URL`)로 `member_inquiry_list`·
  `lesson_inquiry_list`를 프로덕션에서 안정적으로 조회 중**(일/주/월 CPO 자동보고 소스)이라는 걸 확인 →
  이 검증된 인프라(`cpo_report._gas_get`)를 그대로 재사용하기로 결정(중복 로직 0, 파싱 드리프트 위험 0 —
  GAS 응답이 곧 원본 shape이라 재가공이 필요 없음). gviz보다 느리지만(멤버십 5~14초/호출, 실측) 2~3분
  주기 백그라운드 job에는 무해 — 사람이 기다리는 경로가 아니다.
- **scope=all은 이번 스냅샷 범위에서 제외(의도적 보수 결정 — GM 보고 대상).** 실측: 강습 성인
  scope=all 단독 3,525건(멤버십 621건·강습 연간뷰 484+676건의 3~5배). 매 3분마다 이 크기를 통째로
  git 커밋하면 (a) 저장소가 하루 수백MB씩 불어나고 (b) 실질 이득은 작다(scope=all은 상담사가 자주 여는
  기본 화면이 아니라 "전체보기" 토글 — 오늘도 기존처럼 GAS 라이브 6~9초 그대로 유지해도 체감 손실 적음).
  코드도 이미 이 화면만 gviz를 피하고 GAS를 강제하는 보수적 결정을 갖고 있음(시트 숨김행 누락 위험,
  L3792-3793 주석) — 그 결정의 연장선에서 "속도보다 정합성/실용" 원칙을 그대로 적용. **후속 필요 시
  별도 저빈도(예: 시간당 1회) 스냅샷으로 확장 가능**하나 이번 배포 범위 밖.
- 산출물 2개 파일(GM 제안 `inquiry_snapshot_*.json` 패턴 그대로, localStorage 캐시 키 분리와도 대응):
  - `status/inquiry_snapshot_member.json` — `{generated_at_kst, ts, ok, count, rows, warnings}`
  - `status/inquiry_snapshot_lesson.json` — `{generated_at_kst, ts, adult:{year:{ok,count,rows}}, youth:{year:{ok,count,rows}}, warnings}`
- **커밋 절약(repo 건강)**: row 내용(생성시각 제외)이 직전 커밋본과 동일하면 그 파일은 이번 회차에 커밋하지
  않는다(사람 눈에 보이지 않는 변경이라 이득 없음) — 단, 15분 이상 커밋이 없었으면 "정상 가동 중" 하트비트로
  강제 커밋(그래야 job이 죽었을 때 스냅샷이 무한정 "최신"처럼 보이지 않고 신선도 표시가 실제로 벌어짐).
- **동시실행 가드**: `status/.locks/cpo_inquiry_snapshot/` mkdir 락(10분 stale) — 이전 회차가 아직
  돌고 있으면 새 회차는 즉시 스킵 + 로그(조용한 실패 금지).
- **git 직렬화**: `scripts/git_lock.py`의 `git_commit_push()` 재사용(다른 자동화와 동시 커밋 충돌 방지,
  기존 확립된 패턴).
- 실행: `python scripts\cpo_inquiry_snapshot.py` — 실패해도 절대 예외로 죽지 않음(fail-soft), 로그는
  `logs\cpo_inquiry_snapshot.log`.

## 페이지 배선 — `문의회원.html`
- `_SNAP_MEMBER_URL_`/`_SNAP_LESSON_URL_` = RAW_BASE(`raw.githubusercontent.com/.../master/`) 관례
  그대로(다른 다수 페이지가 이미 쓰는 검증된 fetch 패턴 — 신규 패턴 도입 안 함).
- `_snapFetch_(url)` — 1회 메모이즈드 fetch(`cache:'no-store'`), 실패 시 null(throw 안 함).
- `loadDbData()`: 캐시(`_dbCacheLoad()`) 없을 때만 `_dbSnapTryRender_()` 시도 — 배경 `_dbPromise`는
  무변경·무조건 발사. 실 데이터 도착(`_dbRealLoaded=true`) 이후 늦게 스냅샷이 와도 절대 덮어쓰지 않음
  (레이스 가드).
- `lessonLoad(t)`: 동일 패턴을 `scope==='year'`에서만 적용(스냅샷이 없는 `scope==='all'`은 기존
  "불러오는 중…" → GAS 그대로).
- `_dbCacheLoad()`/`_lessonCacheLoad()`가 `ts`도 함께 반환하도록 확장(신선도 표시용, 호출부 1곳씩이라
  블라스트 반경 작음).

## 라이브 검증 계획(시크릿 크롬)
1. 스냅샷 파일 실존·raw.githubusercontent 200 확인.
2. 시크릿 크롬 첫 진입 → 멤버십 목록이 "불러오는 중…" 없이 즉시(스냅샷) 렌더되는지.
3. 스냅샷 생성 이후 새로 들어온 문의(있다면) 또는 인위 지연 문의 재검증 후 반영되는지(배경 gviz 완료 후
   비교).
4. 진행중 편집(WriteBuffer 큐에 항목 존재 상태) 새로고침 → 편집값이 스냅샷 렌더 단계에서도 유지되는지.
5. 스냅샷 파일 강제 훼손(임시) → 페이지가 조용히 3단계(캐시/gviz)로 폴백하는지, 콘솔 warn 존재 확인 후 원복.
6. "N분 전 기준" 텍스트가 실제 스냅샷 `generated_at_kst`와 일치하는지.

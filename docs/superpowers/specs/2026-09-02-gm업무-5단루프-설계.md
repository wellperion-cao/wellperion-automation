# GM업무 5단 순환 루프 — 기획 설계서 (2026-09-02 · 웰리 검수 전 초안)

> GM 확정 루프(2026-09-02):
> **GM업무 → 중간관리자 인계 → 업무SSOT 체크 및 확인(일정) → GM업무 체크 → 일일·주간·월간 진행현황 보고 → (다시 GM업무)**
>
> GM 원문 요지 — "체크리스트가 많아지는데 진행·처리까지 웰리가, 실무진들이랑 소통하면서" /
> "중간관리자들과 카톡으로 소통하면서 업무를 자동으로 처내는 것까지 웰리 주도" /
> 담당 배정 = **③ 중간관리자 방에 넘겨 실장·소장·나우열M 이 나눈다**(웰리가 초안 배정하지 않음) /
> "업무SSOT가 만들어지고 진행 추적까지."

본 설계는 **새 파일·새 화면·새 발신 경로·새 원장을 만들지 않는다**(약속 L21). 기존 4개 원장
(monthly_ops_plan.json · schedule_ssot.json · 업무SSOT 시트(S3) · _queue.json)과 기존 아침
카톡 파이프라인(07:30 내보내기 → 다이제스트 → 07:40~07:58 발송)에 얹는다.
아래 사실은 전부 2026-09-02 파일 실측이다. 확인 못 한 것은 §11에 "미확인"으로 모았다.

## §1. GM께 — 한 장 요약 (비개발자용)

**바뀌는 것 하나** — 지금은 GM업무 카드의 체크리스트(□ 줄)를 GM 이 직접 처리하십니다.
앞으로는 웰리가 그 줄들 중 **실무진 손이 필요한 것**을 골라 아침 ★중간관리자 통(07:50,
이미 매일 나가는 「확인 부탁드릴 것」 절)에 실어 보내고, 실장님·소장님·나우열M 이
**"이건 우리 팀이 하겠다"고 회신**하시면 그 회신을 근거로 업무SSOT(S3)에 등록해
진행을 추적합니다. S3에서 완료 처리되면 GM업무 체크 줄이 ✅로 바뀝니다.

| 단계 | 누가 | 어디서 보이나 |
|---|---|---|
| ① GM업무 (체크리스트) | GM·웰리 | GM업무 화면 (지금 그대로) |
| ② 중간관리자 인계 | 웰리 발신 | 아침 07:50 ★중간관리자 카톡 통 (지금 그대로의 통) |
| ③ 담당 회신 → S3 등록 + 일정 | 실장·소장·나우열M 회신 / 웰리 등록 | 업무SSOT 화면 · 전사일정 |
| ④ GM업무 체크(✅) | 자동(매일 동기화) | GM업무 화면 체크 줄 |
| ⑤ 일일·주간·월간 보고 | 자동 | 08:00 텔레그램 · 금 17:00 주간 통 · 월말 카드 (전부 기존 통) |

**안 바뀌는 것** — ▸담당은 웰리가 정하지 않습니다(방에서 세 분이 나눕니다 · GM 결정).
▸담당 회신이 없으면 S3에 올리지 않습니다(주인 없는 일 금지 · 약속 L23).
▸실무진을 재촉하지 않습니다("N일째" 금지 · gm-report 스킬 §4-2-2). ▸두 카톡 방 발신은

## §3. 담당 표기 규약 — 기존 판정 정규식을 깨지 않는다

실측 정규식(scripts/gm_aide_scan.py:82-83):
- `CHECKLIST_ITEM = ^[□✅]\s*\d+\)` — **줄 머리**만 본다. 「□ 1) …」 형식만 체크 항목으로 센다.
- `DUE_MARK = \(~\s*(\d{1,2})/(\d{1,2})\s*\)` — 줄 **어디에 있어도** 찾는다(search).

따라서 태그는 **줄 끝**에 붙인다. 머리(□ N))와 (~M/D)만 안 건드리면 두 정규식 모두 무사하다.

```
□ 3) 상담실 게시물 준비 (~9/10)                          ← 지금 형식(변화 없음)
□ 3) 상담실 게시물 준비 (~9/10) [담당: 미정]              ← 웰리가 인계 항목으로 표시·발신됨
□ 3) 상담실 게시물 준비 (~9/10) [담당: 이경연 실장 (회신 9/4)] ← 회신 확정·S3 등록됨
✅ 3) 상담실 게시물 준비 (~9/10) [담당: 이경연 실장 (회신 9/4)] ← S3 완료 → 자동 체크
```

- 태그 파서(정규식 `\[담당:\s*([^\]]+)\]`)는 **gm_aide_scan.py 의 CHECKLIST_ITEM·DUE_MARK 옆에
  한 번만** 정의하고 소비자(ops_daily_digest·monthly_ops_sync)는 import 한다 — 판정 로직 복제
  금지(약속 L21 "기존 단일 지점 재사용").
- **S3 쪽 매칭 키는 체크 줄이 아니라 S3 content 에 둔다** — 등록 시 content 끝에
  `[GM업무 {objective_id} {N}번]` 한 줄. 체크 줄에 긴 TODO id 를 박으면 GM 화면이 더러워진다
  (GM 미감 원칙). 역방향(④)은 이 태그로 행을 찾는다.
- ★실측 주의: 현재 9월 카드의 「■ 할 일」 줄 다수가 「□ 1️⃣ …」·「□ 매달 초 …」 형식이라
  `□ N)` 정규식에 **안 걸린다**(2026-09-04 카드 실측). 루프에 태우려면 그 줄들을 「□ N)」로
  고쳐 적는 정비가 1단계에 포함된다 — 정규식을 넓히지 않는다(넓히면 gm_aide 판정 ③⑥⑦의
  의미가 소급으로 바뀐다).
- **(~M/D) 없는 항목은 인계하지 않는다** — 기한 없는 등록은 지연·임박 알림(09:30)이 영영
  못 잡는다. 기한 빈칸은 이미 gm_aide ⑥(완료예정일없음)이 매일 잡아 GM께 올린다(약속 L26⑤).

## §5. 회신 매칭 — 자유 문장에서 담당을 가리는 법과 되돌리기

**전제** — 회신은 사람이 자유롭게 쓴다("그건 저희가 할게요", "소장님 쪽 건 같은데요").
기계 파싱으로 못 가린다. 그래서 **이미 매일 도는 mgr 다이제스트 LLM 판독 패스**(ops_daily_digest
가 ★중간관리자 .txt 를 읽어 이슈 open/resolved 를 가리는 그 패스)에 출력 하나를 얹는다 —
bridge_to_schedule 이 schedules 출력을 얹었던 것과 같은 방식(약속 L21 · 새 LLM 호출 0회).

- **입력**: 전날 인계 항목 목록(체크 줄 원문 + objective_id·항목번호) + 전날 방 대화.
- **출력**: `assignments: [{objective_id, item_no, owner, reply_quote, reply_date}]`.
  owner 는 반드시 **회신 원문 인용(reply_quote)** 과 함께 낸다 — 인용 없는 배정은 버린다
  (약속 L25 "재기 전에 말하지 않는다"의 코드판).
- **owner 검증**: `_OWNER_CHOICES` 7인(ops_daily_digest 실측: 이경연 실장·최준용M·윤병현AM·
  임정은M·백승화 사원·이정헌 소장·나우열M) 밖 이름은 확정으로 안 받는다.
  단 **운영부 실무진 4인이 owner 로 나오면 이경연 실장으로 올린다** — 운영부는 실장 한 사람을
  거친다(약속 L24). 실장이 팀 안에서 나누는 것은 S3 화면에서 실장이 한다.
- **오판 시 되돌리기(두 곳·둘 다 사람이 보이는 화면)**:
  1. 체크 줄의 `[담당: …]` 태그를 지우거나 고친다(monthly_ops_plan.json — GM업무 화면 정본).
  2. S3 등록건을 화면에서 삭제(todo_delete)한다. AI 등록분은 `creator="AI 아침정리"` 로
     식별된다(기존 `_BRIDGE_CREATOR` 재사용) — 사람 등록건과 절대 안 섞인다.
  ledger 의 assignments 기록은 지우지 않는다(경위 보존). 같은 항목은 태그가 지워지면
  다음 아침 다시 인계 목록으로 돌아간다 — 별도 복구 절차 불필요.
- **확정 사실의 사후 보고**: 그날 08:00 텔레그램 1줄(§7)에 「담당확정 n건(누구←무엇)」이
  실린다. GM 이 오판을 아침에 바로 잡을 수 있는 자리다(발신로그·중복발신을 GM 이 잡아 온
  기존 리듬과 같다).

## §6. 업무 SSOT 등록 경계 — "회신으로 확정된 건만"을 코드로 강제

**종전 규칙(실측)** — bridge_to_todo(ops_daily_digest.py:1271~)는 2026-08-12 GM 지시(배589)로
**등록 경로가 코드에서 끊겨 있다**(dry-run 미리보기만 남음). 이유: "실무진들이 할 것까지
다 해버리면 어떻게 해" — AI 가 대신 올리면 그 사람의 일이 사라진다. 2026-08-18 메모리
"AI는 업무 SSOT에 대신 등록 안 함"도 같은 건이다.

**이번 지시로 좁게 다시 연다** — 2026-09-02 GM 지시("업무SSOT가 만들어지고 진행 추적까지")가
그 위에 온다. 단 **전면 재개가 아니다**: 종전 사고(대화에서 담당을 '추정'해 5건 자동 등록)와
이번 것은 다르다 — 이번엔 **그 사람이 제 입으로 맡겠다고 회신한 건**만 올린다. 담당의 일이
사라지는 게 아니라, 담당이 이미 받겠다고 한 일을 대신 적어 주는 것이다.

**코드 강제(관문 하나 · net-zero)** — 죽어 있는 bridge_to_todo 를 새 함수로 복제하지 않고
**그 자리를 좁은 조건부 경로로 고쳐 쓴다**(순증 0 · 약속 L21):

```
등록 허용 조건(전부 만족해야 todo_add 호출 — 하나라도 빠지면 등록 자체가 안 됨):
  ① 출처 = GM업무 체크 줄 (objective_id + item_no 가 실존하고 그 줄이 □ 상태)
  ② assignment 레코드에 reply_quote(회신 원문 인용)·reply_date 가 비어 있지 않음
  ③ owner ∈ _OWNER_CHOICES (운영부 4인 → 이경연 실장 승격 후)
  ④ 그 줄에 (~M/D) 기한 표기 존재 → endDate 로 그대로 옮김 (기한 지어내기 금지 —
     종전 사고의 "7일 뒤 임시 기한" 폴백은 이 경로에 두지 않는다)
  ⑤ 같은 역참조 태그([GM업무 …])가 S3 에 이미 없음 (중복 등록 차단)
조건 밖 호출은 예외를 던진다 — 스위치·플래그 없음(꺼둔 게이트를 남기지 않는다 · L21).
함수 주석에 배589(끊은 경위)와 2026-09-02(좁게 연 경위)를 나란히 적는다.
```

기존의 "대화 이슈 일반 자동 등록 금지"는 그대로다 — 이 조건 ①이 그 경계다.
GM업무 체크 줄에서 출발하지 않은 건은 여전히 등록될 길이 없다.

## §7. 보고 3종 — 전부 기존 통에 얹는다 (새 발신 0)

| 주기 | 통(기존 실측) | 얹는 내용 |
|---|---|---|
| 일일 | 08:00 텔레그램 통합 보고(ceo_morning_pipeline → GM) | 1줄: 「🧭 GM업무 루프 — 인계 n · 담당확정 n(누구←무엇) · 완료 n」. 0·0·0 이면 줄 자체를 뺀다(변화 없는 날 소음 금지) |
| 주간 | 금 17:00 run_weekly_ops_report → ★중간관리자 카톡(build_weekly_report_draft · S3 행 기반 · 킬스위치 ops_digest_send.json 공유) | AI 등록분(creator=AI 아침정리)은 S3 행이므로 **기존 초안에 자동 포함**된다. 절 하나만 추가: 「GM업무 인계건 — 진행 n · 완료 n · 담당 대기 n」 |
| 월간 | monthly_ops_report --mode end(말일 21:00 텔레그램 GM) | 1줄: 해당월 GM업무 카드 체크리스트 소화율 「✅ a / 전체 b」 (CHECKLIST_ITEM 로 세는 실측값 — 요약줄 옮겨적기 아님) |

- 받는 사람이 겹치지 않는다: 일일·월간=GM(텔레그램), 주간=중간관리자(카톡 공유).
- GM업무 화면 자체가 상시 진행현황판이다(체크 줄이 ✅로 바뀌는 곳) — 보고는 변화 요약만.

## §8. 실패·정체 처리 — 재촉하지 않고 굴리는 법

| 상황 | 처리 (전부 기존 기제) |
|---|---|
| 회신이 안 온다 | relay 델타·재알림 기제 그대로 — 내용이 안 바뀌면 다시 안 싣고, RELAY_STALE_DAYS 묵으면 한 번 더 싣는다(send_ops_digest 실측). "N일째" 같은 압박 표기는 금지(스킬 §4-2-2) — 문구는 항상 처음처럼 |
| 오래 담당이 안 정해진다 | 실무진을 더 조르지 않는다. **7일 무회신이면 GM 에스컬레이션 1줄**(08:00 보고의 루프 줄에 「담당 대기 7일+ n건」) — 방향은 GM 이 정한다(재촉 대신 GM 이 오프라인·미팅에서 정리). 그동안 체크 줄은 [담당: 미정] 그대로 — 빈칸을 지어 채우지 않는다(L23) |
| 회신은 왔는데 애매하다(인용 불충분) | 확정으로 안 받는다(§5 — 인용 없는 배정 폐기). 항목은 인계 목록에 남고, 웰리가 다음 발신 때 그 항목의 물음만 또렷하게 고쳐 쓴다 |
| S3 등록 후 진행이 멈춘다 | 기존 09:30 지연·임박 알림 + 금 17:00 주간 초안이 잡는다 — 이 루프가 새로 할 일 없음 |
| LLM 이 담당을 오판했다 | §5 되돌리기 2곳 + 08:00 사후 보고로 다음날 아침 안에 잡힌다 |
| 아침 파이프라인 자체가 죽었다 | 기존 실패 처리 그대로(발송 실패 알림 _kakao_fail_notify · 예약작업 실패 기록). 이 루프는 하루 밀릴 뿐 상태를 잃지 않는다 — 모든 상태가 원장(파일·시트)에 있고 메모리에 없다 |

## §9. 착수 순서 — 4단계와 완료 판정 (각 단계 = 재현 가능한 실증거)

**1단계 — 표기 규약·인계 발신** (□ N) 정비 + [담당:] 태그 파서 + 인계 배 생성)
- 작업: 9월 GM업무 카드의 「□ 1️⃣」류 줄을 「□ N)」로 정비 / OWNER_TAG 정규식을 gm_aide_scan
  에 정의 / 웰리가 인계 항목에 [담당: 미정] 태그 + staff_message 3줄 규칙(스킬 §4-2-2)으로
  배 생성(즉시 DONE + relay_until_replied=true). 신규 전달 문구는 첫 회차 초안→GM 승인
  (2026-08-06 확정 규칙 유지) 후 발신, 이후 같은 형식은 정기 자동 발송(약속 L24 예외 범주).
- 완료 판정: ⓐ gm_aide_scan 드라이런에서 9월 카드 체크 항목이 ⑥⑦ 판정에 정상 집계
  ⓑ send_ops_digest --dry-run(또는 --relay-preview)에 인계 항목이 「🧾 확인 부탁드릴 것」
  절로 렌더 ⓒ 실발신 1회의 발신 로그.
**2단계 — 회신 판독·담당 확정** (assignments 출력 + 체크 줄 태그 갱신)
- 완료 판정: 실제 회신 1건이 다음날 아침 실행에서 ledger.assignments 에 인용과 함께 기록되고,
  monthly_ops_plan.json 해당 줄이 [담당: X (회신 M/D)] 로 바뀐 git diff. + 인용 없는 가짜
  assignment 가 버려지는 셀프테스트(네트워크 없이 도는 함수 테스트 — 기존 _selfcheck 관례).
**3단계 — S3 등록 경계 + 역방향 ✅** (§6 조건부 경로 + monthly_ops_sync 꼬리 동기화)
- 완료 판정: ⓐ 확정 1건이 S3 에 creator=AI 아침정리·역참조 태그로 등록(화면 실측)
  ⓑ 조건 ①~⑤ 하나라도 빠진 입력이 예외로 거부되는 셀프테스트 ⓒ S3 완료 처리 → 다음
  sync 에서 □→✅ 바뀐 git diff.
**4단계 — 보고 3종 얹기** (§7 세 줄/절)
- 완료 판정: 08:00 보고·금 17:00 주간 초안·월말 카드 각각의 드라이런 출력에 해당 줄이
  실리고, 0건일 때 줄이 빠지는 것까지 확인.

단계 간 의존: 1→2→3 순차(앞 단계 산출이 뒷 단계 입력). 4는 3과 병렬 가능.
각 단계 완료 시 커밋·푸시 즉시(약속 L13·L15) + AI 진행현황방 1줄(notify_gm_progress).

## §10. 하지 않을 것 (경계 목록)

1. **새 화면 없음** — GM업무.html·월간운영계획.html·업무SSOT 화면 그대로. 루프 전용 대시보드 금지.
2. **새 알림·새 발신 슬롯 없음** — 07:40~07:58 카톡 5통·08:00/21:00 텔레그램·09:30 지연알림·
   금 17:00 주간·월초/말 카드 외 발신 신설 금지. 발신 관문은 kakao_report_sender 하나(L21·L24).
3. **새 원장 없음** — 상태는 monthly_ops_plan.json(체크 줄)·_queue.json(배)·
   ★중간관리자 _digest_ledger.json(회신)·S3 시트(실행)·schedule_ssot(일정) 5곳뿐.
   "루프 상태 파일" 신설 금지.
4. **새 스크립트·새 예약작업 없음** — gm_aide_scan·ops_daily_digest·send_ops_digest·
   monthly_ops_sync·monthly_ops_report·daily_scheduler 기존 6개 안에서만 고친다.
5. **웰리가 담당을 초안 배정하지 않는다** — [담당:] 확정값은 회신 인용이 있을 때만(GM ③ 결정).
6. **회신 확정 없는 S3 등록 없음** — §6 조건부 경로 밖 todo_add 호출 금지. 기한 폴백(+7일) 금지.
7. **실무진 재촉 문구 없음** — "N일째"·미회신 누적 표기 금지. 정체는 GM 에게만 1줄.
8. **판정 로직 복제 없음** — CHECKLIST_ITEM·DUE_MARK·OWNER_TAG·중복판정은 각 1곳 정의·import.
9. **LLM 호출 신설 없음** — 회신 판독은 기존 mgr 다이제스트 패스에 출력 필드만 추가.
10. **시로·시뽀 라인 접촉 없음** — 나우열M 은 인계 수신자(중간관리자)로만 등장(규약 v1.1 그대로).

## §11. 미확인 목록 (열어 보지 못한 것 — 지어 적지 않음)

- **S3 GAS(todo_add)의 owner 칸 서버측 검증 여부** — .deploy-todo/업무&결재 현황.js 에서
  todo_add 액션 존재(2772행)는 확인했으나 owner 값 검증 로직 유무는 본문 미독. 클라이언트
  (§6 ③)에서 막으므로 설계엔 영향 없음.
- **staff_to 에 개인이 아닌 문자열("중간관리자 세 분")을 넣었을 때의 표시** — 코드상 자유
  문자열 그대로 사람 묶음 헤더에 찍힌다(send_ops_digest:1306 실측)만, 실발신 화면 확인은 안 함.
  담당 미정 인계 항목의 수신 표기는 1단계 실발신 때 확인한다.
- **「확인 부탁드릴 것 11건」(오늘 발송분)** — 과제 지시문에 적힌 실측값을 인용한 것. 본
  설계 세션에서 발송본을 직접 열어 세지는 않았다.
- **mgr 다이제스트 LLM 패스의 프롬프트 원문**(ops_daily_digest 중반부) — assignments 필드를
  얹을 정확한 삽입 지점은 2단계 착수 시 해당 함수를 열어 정한다.
- **wellperion-gm-report 스킬 §5(항로 리스트업 양식)** — 이번 루프와 직접 접점 없어 미독.

작성일 2026. 09. 02.
작성 AI 시토  ·  근거 D-Live Messaging Server API Reference v1.2
지금은 회원께 알려드리는 일을 사람이 손으로 한다. 접수를 받아도, 문의를 남기셔도, 휴회가 반영돼도 회원은 직접 물어보셔야 안다. 문자를 붙이면 그 세 순간에 자동으로 한 통이 나간다. 딜라이브 API 는 표준 REST 방식이라 지금 쓰는 구조에 그대로 얹을 수 있다 — 다만 계정·발신번호가 나와야 한 줄도 못 보낸다. 9/4 미팅에서 받아야 할 것을 오른쪽에 정리했다.

어떻게 붙이나 — 발신 창구는 하나만

항목내용
발신 창구어디에 둘지는 아래 「연결」 결과에 달렸다. 접수·문의·휴회가 전부 구글 앱스스크립트 위에 있어 그쪽이 자연스럽지만, 딜라이브가 발신 IP를 등록받는 방식이면 앱스스크립트는 못 쓴다(구글 서버에서 나가므로 IP가 매번 다르다). 그때는 사내 PC(파이썬)가 창구가 된다. 어느 쪽이든 창구는 하나다 — 둘이면 같은 문자가 두 번 나간다.
접속HTTPS 전용 · 58.143.1.130:7443 · 요청·응답 모두 JSON(UTF-8)
연결 실측
2026-09-02		계정은 받았는데 서버에 안 닿는다. 원인을 세 번 갈라서 확인했다 — ① 딜라이브 서버의 443 포트는 열려 응답한다(서버는 살아 있다) ② API 포트 7443 만 21초 무응답 ③ 우리 회선이 그 포트를 막는지 확인하려 다른 서버의 같은 포트에 붙어 보니 정상이었다. → 우리 문제가 아니라 딜라이브가 등록된 IP 에만 7443 을 여는 구조다. 우리 공인 IP = 114.207.50.85
인증아이디·비밀번호로 토큰을 받아 1시간 쓰고, 만료 5분 전에 갱신한다. 토큰은 코드에 적지 않고 앱스스크립트 속성에 보관한다.
한 번에 한 통API 규격상 한 요청에 한 통이고, 결과를 받기 전 다음 통을 보내면 안 된다. 여러 명에게 보낼 일이 생기면 줄 세워 보낸다.
길이한글 45자까지 SMS, 넘으면 LMS(제목 필요·한글 1,000자). 위 문구는 전부 SMS 안에 들어가게 썼다.
중복 차단문자마다 고유 키를 접수번호로 만든다(예: RCP-145-DONE). 같은 키는 서버가 거른다 — 버튼을 두 번 눌러도 두 번 안 나간다.
보냈는지 확인딜라이브가 발송 결과를 따로 보관한다. 10분마다 결과를 받아 실패한 건만 업무보고방에 알린다. 성공은 조용히 지나간다.

IP 없이 가는 길이 있나 — 직접 찾아봤다

GM 물음(2026-09-02)에 답하려고 우회로를 세 갈래로 실제로 시험했다. 결과는 아래 「막힘」 표다.

시험한 우회로결과 — 실측
다른 포트에 API가
또 열려 있나		없다. 같은 서버 443 에 붙어 보니 딜라이브 레터 웹 화면이 뜬다(인증서 발급자 = D'LIVE Message Server). API 주소를 세 가지로 넣어 봤으나 전부 「없는 주소」로 응답.
웹 화면으로
대신 보내나		이 계정으로는 못 들어간다. 로그인 1회 시도 — 실패(잠김 위험이 있어 더 시도하지 않았다). 받은 계정이 API 전용이고 웹 화면 계정은 따로인 것으로 보인다.
주소(도메인)로
우회되나		안 된다. 서버 인증서에 도메인이 없고 IP 하나만 적혀 있다 — 다른 이름으로 들어가는 문이 애초에 없다.
그래서 남는 길내용판단
① 사무실 IP 등록지금 IP 114.207.50.85 등록. 가장 빠르다. 유동 IP 면 바뀔 때마다 끊긴다 — 고정인지 함께 확인.지금은 이것
② 고정 IP 서버 경유계획 중인 클라우드 서버(AWS) 하나만 등록해 두고 모든 문자를 그 서버가 보낸다. 사무실 IP 가 바뀌어도 안 끊긴다.중기 정답
③ 딜라이브에 확인IP 제한 없이 토큰만으로 쓰는 방식이 있는지, 알림톡 창구가 있는지. 있으면 ①②가 필요 없다.먼저 물을 것
④ 업체를 바꾼다국내 문자 API 중에는 IP 등록 없이 키만으로 쓰는 곳이 있다. 다만 딜라이브는 이미 미팅까지 잡혀 있어 ③의 답을 듣고 판단하는 것이 순서다.마지막 수단

▸ ①과 ②는 고르는 게 아니라 순서다. 지금은 ①로 켜고, AWS 서버가 서면 ②로 옮긴다 — 옮길 때 딜라이브에 IP 한 줄만 바꿔 달라고 하면 된다.

9/4 미팅에서 받아야 할 것 — 1번이 지금 막혀 있다

  1. 발신 IP 등록 — 가장 급하다. 계정을 받았는데 서버에 아예 닿지 않는다. 우리 IP 114.207.50.85 등록을 요청한다. (등록 방식이면 구글 서버 경유가 불가해 발신 창구를 사내 PC로 잡아야 한다 — 설계가 갈리는 지점)
  2. API 아이디·비밀번호 — 받음(2026-09-02). 테스트용이 따로 있는지는 확인 필요
  3. 발신번호 — 받음 02-6261-1200. 사전 등록 절차가 끝난 번호인지 확인 필요
  4. 테스트 환경 — 실제 회원께 안 나가고 시험해 볼 방법이 있는지
  5. 요금 — 건당 단가, 월 최소 사용료, 실패한 건도 과금되는지
  6. 속도 제한 — 1초/1분당 몇 통까지인지 (문서에 "정책에 따라 제한"이라고만 적혀 있다)
  7. 발신 서버 IP 등록이 필요한지 (필요하면 우리 쪽 고정 IP 확인이 선행)
  8. 광고성 여부 판정 — 위 세 문구는 안내성으로 보는지, 「(광고)」 표기·수신거부번호가 필요한지
  9. 알림톡도 같은 계정으로 되는지 — 문자보다 싸고 읽힘이 좋아 나중에 갈아탈 수 있다

시토 의견 — 이렇게 하시길

  • ③휴회부터 켠다 (GM 지시 2026-09-02). 지금 시트에서 손으로 정리해 보내고 있어 사람 손이 가장 많이 드는 자리다. 건수도 적고 담당자가 버튼을 눌러 보내는 방식이라 잘못 나갈 위험이 낮다. ②문의 폼은 셋업·테스트·가이드를 마친 뒤 공유하고 켠다.
  • 진행 변동 안내는 버튼으로만. 자동으로 걸면 담당자가 상태를 고칠 때마다 회원 휴대폰이 울린다. 사람이 "지금 알려도 된다"고 판단할 때만 나가야 한다.
  • 문구는 시트에 두고 화면에서 고친다. 코드에 문장을 박으면 문구 한 줄 바꾸는 데 배포가 필요하다. 실무진이 직접 고칠 수 있어야 오래 간다.
  • 회원 번호가 없는 접수는 그냥 넘긴다. 익명 접수·번호 오기입이 있다. 못 보내는 건 조용히 건너뛰고 화면에만 「번호 없음」으로 표시한다.
  • 보낸 기록을 접수 옆에 남긴다. 언제 무슨 문자가 나갔는지 화면에서 보여야 "안 받았다"는 말에 답할 수 있다.
  • 야간에는 안 보낸다. 21시~08시 발송은 다음 날 아침으로 미룬다(예약 발송 기능이 API 에 있다).

AWS 로 간다면 — 이렇게 된다

항목내용
무엇을 두나이미 계획된 서버(EC2)에 고정 IP 한 개를 붙인다. 딜라이브에는 그 IP 하나만 등록한다. 사무실 인터넷이 바뀌든 직원 PC 가 꺼져 있든 문자는 그 서버에서 나간다.
누가 부르나접수·문의·휴회 화면은 그 서버에 「이 번호로 이 문구 보내줘」 한 줄만 보낸다. 딜라이브 계정·토큰은 화면이 모르고 서버만 안다 — 비밀번호가 화면 코드에 안 들어간다(지금 방식보다 안전하다).
서버가 하는 일① 토큰 받아 두고 만료 전 갱신 ② 한 번에 한 통씩 줄 세워 발송 ③ 10분마다 발송 결과를 받아 실패한 건만 업무보고방에 알림 ④ 야간(21~08시) 건은 아침으로 미룸
순서1 GM AWS 계정 개설(이미 대기 중인 건) → 2 서버 만들고 고정 IP 발급 → 3 딜라이브에 그 IP 등록 요청 → 4 문의 폼부터 시험 발송
비용·부담서버 한 대와 고정 IP 유지비가 든다(금액은 AWS 착수 건에서 예산과 함께 잡는다). 관리할 것이 하나 늘어나는 대신 IP 가 바뀌어 문자가 조용히 끊기는 사고가 없어진다.

실무진께 여쭐 것 — 웰리에게 넘김

문구를 확정하려면 사람에게만 답이 있는 것이 셋 있다 — 이경연 실장(진행 상황이 바뀔 때 어느 단계에서 알릴지) · 임정은M(휴회 안내에 기간을 넣어도 되는지) · 리셉션(문자 받은 회원이 전화로 되물으실 것). 사람 방 발신은 웰리 몫이라 2026-09-02 에 배로 넘겼다. 급하지 않다 — 연결이 뚫린 뒤 문구를 확정하면 된다.

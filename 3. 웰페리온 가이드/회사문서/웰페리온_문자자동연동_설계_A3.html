지금은 회원께 알려드리는 일을 사람이 손으로 한다. 접수를 받아도, 문의를 남기셔도, 휴회가 반영돼도 회원은 직접 물어보셔야 안다. 문자를 붙이면 그 세 순간에 자동으로 한 통이 나간다. 딜라이브 API 는 표준 REST 방식이라 지금 쓰는 구조에 그대로 얹을 수 있다 — 다만 계정·발신번호가 나와야 한 줄도 못 보낸다. 9/4 미팅에서 받아야 할 것을 오른쪽에 정리했다.

항목내용
발신 창구구글 앱스스크립트(GAS) 한 곳에만 문자 발신 함수를 둔다. 접수·문의·휴회 세 곳이 이미 전부 GAS 위에서 돌기 때문이다. 화면·파이썬에서 직접 문자를 쏘지 않는다 — 창구가 둘이 되면 같은 문자가 두 번 나간다.

9/4 미팅에서 받아야 할 것 — 이게 없으면 못 켠다

  1. API 아이디·비밀번호 (테스트용·운영용 구분되는지)
  2. 발신번호 — 대표번호 02-6261-1200 을 쓸 수 있는지, 사전 등록 절차가 따로 있는지
  3. 테스트 환경 — 실제 회원께 안 나가고 시험해 볼 방법이 있는지
  4. 요금 — 건당 단가, 월 최소 사용료, 실패한 건도 과금되는지
  5. 속도 제한 — 1초/1분당 몇 통까지인지 (문서에 "정책에 따라 제한"이라고만 적혀 있다)
  6. 발신 서버 IP 등록이 필요한지 (필요하면 우리 쪽 고정 IP 확인이 선행)
  7. 광고성 여부 판정 — 위 세 문구는 안내성으로 보는지, 「(광고)」 표기·수신거부번호가 필요한지
  8. 알림톡도 같은 계정으로 되는지 — 문자보다 싸고 읽힘이 좋아 나중에 갈아탈 수 있다

시토 의견 — 이렇게 하시길

  • 세 개를 한꺼번에 켜지 않는다. ②문의 폼부터 켠다 — 하루 5~10건이라 양이 적고, 실패해도 회원 불편이 가장 작다. 2주 무사고면 ①접수처, 그 다음 ③휴회.
  • 진행 변동 안내는 버튼으로만. 자동으로 걸면 담당자가 상태를 고칠 때마다 회원 휴대폰이 울린다. 사람이 "지금 알려도 된다"고 판단할 때만 나가야 한다.
  • 문구는 시트에 두고 화면에서 고친다. 코드에 문장을 박으면 문구 한 줄 바꾸는 데 배포가 필요하다. 실무진이 직접 고칠 수 있어야 오래 간다.
  • 회원 번호가 없는 접수는 그냥 넘긴다. 익명 접수·번호 오기입이 있다. 못 보내는 건 조용히 건너뛰고 화면에만 「번호 없음」으로 표시한다.
  • 보낸 기록을 접수 옆에 남긴다. 언제 무슨 문자가 나갔는지 화면에서 보여야 "안 받았다"는 말에 답할 수 있다.
  • 야간에는 안 보낸다. 21시~08시 발송은 다음 날 아침으로 미룬다(예약 발송 기능이 API 에 있다).
